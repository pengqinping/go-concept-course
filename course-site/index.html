01 · 包、模块与构建边界

一句话模型：包是可见性与编译单元，模块是依赖与版本边界；构建标签在编译前决定"哪些文件存在"。

先看一个现象

demo 里 printer 子包就在隔壁目录，main.go 里却出现了两个"意外"：

go
import "example.com/go-course/01-package-module/printer"

func main() {
	fmt.Println(printer.Print("Go", 2))    // 正常
	fmt.Println(printer.decorate("Go", 2)) // 编译失败
}

你以为 import 写的是"隔壁目录的相对路径"，实际它写的是模块路径 + 包目录拼出的完整路径——写成 import "printer" 反而找不到包。你以为 decorate 只是"不建议外部调用"，实际它首字母小写、未导出，编译器直接拒绝：这不是风格建议，是语言边界。

再往前一步：如果三个 .go 文件里有两个定义了同名函数 platformMessage，编译却不报"重复定义"。你以为编译器会读完目录里所有文件；实际构建标签在编译开始前就把不匹配的文件筛掉了，编译器根本没见过它们。编译不是从"目录里的全部文件"出发，而是从"被选中的文件"出发。

先建立直觉

记住两件事的位置：大小写这条线画在包与包之间；三道关卡按时间先后排序——模块解析最早，文件筛选次之，编译最后。后面每一步都在回答"这道关卡为什么放这里"。

机制拆成四步

1. 包：目录只是住址，package 声明才是身份

同一个目录下的文件必须声明同一个 package，编译器以包为单位编译。为什么以包为单位而不是以文件为单位？因为包是"一起编译、一起复用"的最小单元：改包里任何一个文件，整个包重新编译；包内标识符互相直接可见，不用 import 也不用前缀。

跨包的规则只有一条：标识符首字母大写即导出。为什么选首字母而不是 export 关键字？可见性写在定义处，读代码时一眼可辨，不需要工具或文档确认。于是 printer.Print 能被 main 调用，printer.decorate 不能——后者也没有"私有但可绕过"的口子，跨包调用就是编译失败。

go
package printer

func Print(word string, edge int) string  { return decorate(word, "=", edge) }
func decorate(word, deco string, edge int) string { /* 未导出：只有包内可见 */ }

同目录、同包的另一个文件不需要这些仪式——互相直接用，连 import 都不写：

go
// printer/page.go 与 printer.go 同包
package printer

func Page(s string) string { return decorate(s, "-", 4) }

包内不设防，包外不放过：可见性只有一个粒度，就是包。

还有一个隐式边界：internal/ 目录下的包，只能被同一个模块内、以 internal 祖先目录为根的那部分代码导入。放进去的代码天然是"模块私有"的。

2. 模块：import 路径的前缀与版本边界

go.mod 第一行 module example.com/go-course/01-package-module 给模块内所有子包一个公共前缀。导入路径 = 模块路径 + 包在模块内的相对目录，所以 printer/ 目录要写 example.com/go-course/01-package-module/printer。为什么不让 import 写相对路径？因为相对路径只在你的磁盘上成立，模块路径让这个包在任何人、任何机器上都能被唯一引用。

text
module example.com/go-course/01-package-module

go 1.24

读完这一行就能推导入路径：模块内任何目录的包，路径都是"这行 + 相对目录"。版本怎么进路径，看两个例子：

text
example.com/shop/catalog/item  → 模块 example.com/shop 里 item/ 目录的包
example.com/greeting/v2        → v2 写进路径本身，v1 与 v2 是两个模块

模块同时是版本边界：require 声明依赖哪个版本，go.sum 记录每个依赖内容的校验和，防止拿到的代码与声明不一致。多个依赖共同要求同一模块时，按最小版本选择取"满足所有要求的最低版本"，不会因为更高的版本存在就自动升级。一个细节：主版本从 v2 起要写进模块路径本身（.../v2），让新旧大版本作为两个不同模块共存。

3. 构建标签：编译前的文件筛选

//go:build linux 写在文件顶部、package 之前、隔一个空行，意思是"本文件只在目标平台为 linux 时参与构建"。&&、||、! 可以组合；message_linux.go 这类文件后缀是等价的简写。没选中的文件不是"编译时跳过"，而是从一开始就不存在——所以同名的重复定义不报错，文件里未使用的 import 也不报错。

为什么要放在编译之前？因为平台差异常常是 API 级别的：某个系统调用只在 Linux 上存在，if runtime.GOOS == "linux" 这种运行时判断救不了编译——代码必须先通过类型检查。把互斥的实现放进按标签选择的文件里，另一个平台才编得过。

自定义标签用于可选功能，机制完全相同：

go
//go:build demo

package main

func debugBanner() string { return "DEBUG BUILD" }

平时 debugBanner 根本不存在；go run -tags demo . 时它才参与编译——想加调试能力就加标签，不必为调试代码留一个运行时开关。

与其猜，不如问工具：

bash
go list -f '{{.GoFiles}}' .             # 本机这次构建用了哪些文件
GOOS=linux go list -f '{{.GoFiles}}' .  # 交叉目标会用哪些文件

4. go:embed：把文件变成编译期输入

go
//go:embed banner.txt
var banner string

嵌入路径相对源文件所在目录，与程序运行时的工作目录无关；嵌入发生在编译期，banner 只是拿到初始值。为什么做成编译期而不是运行时读文件？因为静态资源随二进制一起交付，部署时少一个"文件没拷齐"的故障点——代价是改了文件必须重新构建，且嵌入不等于加密，拿到二进制的人能提取内容。只嵌一个变量用 _ "embed" 空白导入；要嵌入一组文件就声明 embed.FS。嵌入类型按用途选：

  • string：文本、模板、提示语。
  • []byte：需要按字节处理的数据。
  • embed.FS：一组文件，用 //go:embed assets/* 一并收进来。

  • "同一个目录就是同一个包，目录名就是包名" → 身份来自每个文件顶部的 package 声明；目录只是磁盘布局。目录名与包名可以不同，import 路径末段与包名也可以不同——读代码时两个都要看。

02 · 赋值到底复制了什么

一句话模型：Go 里所有赋值都是值拷贝；Slice/Map/Channel 这类看起来像引用的类型，拷贝的是描述符，描述符指向共享的底层数据。

先看一个现象

同样的两个符号 b := a，结果却不一样：

go
type Point struct{ X, Y int }
p := Point{X: 1, Y: 2}
q := p
q.X = 99
fmt.Println(p.X) // 1

s := []int{1, 2, 3}
t := s
t[0] = 99
fmt.Println(s[0]) // 99

你以为两句都是"复制一份"，所以都互不影响；实际 struct 真的复制了整块数据，slice 只复制了三个数字，两个变量仍盯着同一个数组。

再把 slice 换成数组，只差两个字符，行为又翻回去：

go
a := [3]int{1, 2, 3}
b := a
b[0] = 99
fmt.Println(a[0]) // 1

还有一个更常见的困惑：把 slice 传进函数，append 之后外面的长度没变。

go
func add(v []int, x int) []int { return append(v, x) }
s := []int{1, 2, 3} // len=3 cap=3
t := add(s, 4)
fmt.Println(len(s), len(t)) // 3 4

你以为函数改到了同一个 slice；实际它拿到的是描述符副本，只能把新描述符返回给你。s 的长度没变，不是因为没共享，而是因为 len 本来就存在描述符里、是各自的一份。

[3]int 是整块值，[]int 是一个描述符。判断复制的后果，靠的不是"这类型听起来像不像引用"，而是这个值里到底装了什么。

先建立直觉

图里那个 ptr 是整篇的枢纽。记住它，后面每一步都在回答"这个 ptr 什么时候变、什么时候不变"。

机制拆成五步

1. 赋值搬运的是值，不是变量

b := a 在右侧求值的那一刻，把 a 的值搬进 b 的存储；搬完之后两者没有任何关系。对 int、struct、array 来说，值就是数据本身，所以复制等于复制整块。

为什么函数传参、range 赋值、结构体字段赋值都遵守同一条？因为它们本质上都是赋值，Go 没有为它们另设一套"引用传递"规则。于是 reset(v int) 里改 v 动不了外面的变量；for _, item := range items 拿到的是元素副本，改 item 动不了切片里的元素（要改就得用下标）。

go
func reset(v int) { v = 0 }
n := 42
reset(n)
fmt.Println(n) // 42

items := []int{1, 2, 3}
for _, item := range items { item = 99 }
fmt.Println(items) // [1 2 3]

这两段都容易看走眼：函数明明"收到了"参数，range 明明"遍历到了"元素，改动却原地消失。原因不是它们特殊，而是收到的是副本。

2. Slice 的值是三元组描述符

[]int 变量里装的不是数组，而是 (指向底层数组的指针, len, cap)。为什么这样设计？为了让传参和赋值不搬数据——一个百万元素的 slice 传进函数，复制的永远是三个机器字，而不是八兆字节。

于是 t := s 复制出了两个指针字段相同的描述符，改 t[0] 就是改那个共享元素。注意 len 和 cap 是各自独立的副本：对 t 做 t = t[:1] 只缩短 t 的长度，s 的长度不变。共享的是数组，不是描述符。

go
s := []int{1, 2, 3} // ptr → [1 2 3], len=3, cap=3
t := s              // 同样的 ptr, len, cap
t = t[:1]           // 只改 t 的 len
fmt.Println(len(s), len(t)) // 3 1

不同的一揽子类型，复制后共享的范围也不一样：

类型变量的值是什么b := a 搬走了什么改 b 的元素会怎样
int / Point / [3]int数据本身整块数据与 a 无关
[]int(ptr, len, cap)三个数改共享数组，a 看得到
map / chan指向运行时结构的指针一个指针同一张表 / 同一个通道

3. 共享的边界在 append：cap 够不够

append 先检查剩余容量。够，就往同一数组的空位写，只让返回的 slice 变长——原 slice 的 len 不变，新元素落在它的长度之外，暂时看不见；但如果之后改新 slice 里落在原范围内的元素，原 slice 立刻看得到。不够，就分配新数组、复制旧元素、写入新值，返回的 slice 指向新数组，从此与原 slice 分离。

为什么要这么绕？扩容要搬数据，是昂贵操作；cap 预留的空位把多次 append 的成本摊薄了。代价就是"共享还是分离"取决于容量，而不是取决于你用了哪个变量。这里还有个硬约束：append 必须接住返回值。写 append(s, 4) 不接收，一旦触发扩容，那个装着新数组的描述符就被丢掉了。

4. Map 和 Channel 没有"长度维度"的分离

map 变量的值是指向运行时 hmap 的指针，channel 同理。m2 := m 之后两者永远指向同一张表：写 m2 立刻能在 m 上看到，也没有"扩容后分离"这种退路。

为什么 slice 能分离而 map 不能？因为 slice 把 len、cap 暴露成可独立变化的字段，append 可以顺理成章地让描述符改指新数组；map 没有这样的常规入口。想让两份 map 分开，只能重新 make，再逐键复制。

go
m := map[string]int{"a": 1}
m2 := m
m2["b"] = 2
fmt.Println(len(m)) // 2，同一张表

fresh := make(map[string]int, len(m))
for k, v := range m { fresh[k] = v }
fresh["a"] = 99
fmt.Println(m["a"]) // 1，这次真的分开了

5. 赋值还要求两边类型一致：转换不会自动发生

复制讲完，还有一条赋值的前置规则：两边必须是同一类型。var a int64 = 300; var b int32 = a 直接编译报错——为什么 Go 拒绝自动转换？因为窄化转换会悄悄丢数据，与其让编译器替你决定怎么丢，不如强制你写 int32(a) 并承认这一点。

唯一的例外是无类型常量：var b int32 = 300 合法，因为字面量 300 在写下时还没有固定类型，它会在赋值处按需变成 int32；一旦超出 int32 的表示范围，这一行同样报错。而 c := 300 得到的是 int（常量独立声明时的默认类型），之后 var d int32 = c 仍要显式转换——"字面量能隐式转换，变量永远不能"。

动手验证

动手验证改元素与触发扩容，看原 slice 何时跟着变

先预测：把 t[0] 改成 99 后 s[0] 是多少？

运行：cd examples/minimal/02-value-semantics && go run .（标有「可调参数」的常量就是旋钮）

go
package main

import "fmt"

// 可调参数
const (
	baseLen   = 3 // 初始元素个数
	extraRoom = 1 // 第一组预留的额外容量；改成 0 会让第一组 append 也扩容
)

func show(name string, s []int) {
	fmt.Printf("%-10s %v  len=%d cap=%d\n", name, s, len(s), cap(s))
}

func filled(n, capHint int) []int {
	s := make([]int, n, capHint)
	for i := range s {
		s[i] = i + 1
	}
	return s
}

func main() {
	// ① struct：值就是整块数据，复制后互不相干
	type Point struct{ X, Y int }
	p := Point{X: 1, Y: 2}
	q := p
	q.X = 99
	fmt.Printf("struct     p=%+v  q=%+v   （改 q 不影响 p）\n", p, q)

	// ② array：和 struct 一样是整块值
	arr := [4]int{1, 2, 3, 4}
	arr2 := arr
	arr2[0] = 99
	fmt.Printf("array      arr=%v  arr2=%v （改 arr2 不影响 arr）\n", arr, arr2)

	// ③ slice：复制的是描述符，两个变量指向同一底层数组
	s := filled(baseLen, baseLen+extraRoom)
	show("s 初始", s)
	t := s
	t[0] = 99
	show("s 改后", s)
	show("t 改后", t)

	// ④ append：cap 够 -> 仍共享；cap 不够 -> 新数组，从此分离
	shared := filled(baseLen, baseLen+extraRoom)
	shared2 := append(shared, 100)
	shared2[0] = 77
	fmt.Println("--- append 有空位 ---")
	show("shared", shared)
	show("shared2", shared2)
	fmt.Printf("shared[0]==77 ? %v\n", shared[0] == 77)

	separate := filled(baseLen, baseLen)
	separate2 := append(separate, 100)
	separate2[0] = 77
	fmt.Println("--- append 触发扩容 ---")
	show("separate", separate)
	show("separate2", separate2)
	fmt.Printf("separate[0]==77 ? %v\n", separate[0] == 77)
}

  • "Go 是引用传递" → 只有值传递。slice 的"引用行为"来自值里面那个指针。反证：函数里 s = append(s, x) 若触发扩容，外面的 s 长度不会变——如果真是引用传递，它会变。
  • "数组和 slice 差不多" → [3]int 是整块值，复制即分离；[]int 是描述符，复制后仍共享。类型字面量只差两个字符，语义差一整个层级。
  • "append 后原 slice 能看到新元素" → 原 slice 的 len 永远不会变；它只是可能有元素被覆盖。扩容之后连元素都不共享。判断顺序：先看 cap，再分清问的是长度还是元素。

03 · 字符串与 Map 的边界

一句话模型：字符串是只读字节序列，range 按码点走、索引按字节走；Map 是无序哈希表，读零值安全、写会扩容、nil 不能写。

先看一个现象

同一段文字，三种"数一下"给出三个答案：

go
s := "Go语言"
fmt.Println(len(s))         // 8
fmt.Println(len([]rune(s))) // 4
for i := range s { fmt.Print(i, " ") } // 0 1 2 5

你以为 len 数的是"几个字"，实际它数的是字节数：G、o 各占 1 字节，语、言各占 3 字节。你以为 range 给的下标是"第几个"，实际是字节偏移——语 从第 2 字节开始占 3 个字节，所以下一个码点直接从 5 跳过去。

换成 Map，是另一种意外：

go
var m map[string]int
fmt.Println(m["go"]) // 0：读一个不存在的键，安然无恙
m["go"] = 1          // panic: assignment to entry in nil map

读不存在的键返回零值、不报错；写却当场 panic。而且每次运行遍历 m 的顺序都可能不同——不是你代码写错了，是运行时故意随机化遍历起点。

先建立直觉

上半只需记住一句话：索引和 len 永远站在字节这边，range 站在码点这边。下半记住三种状态可以区分：键不存在、值为零、已删除。

机制拆成四步

1. 字符串：只读的字节序列

string 变量里装的是指向只读字节的指针加长度。s[i] 取出的是 byte（uint8），不是"字符"；len 返回字节数。为什么设计成只读？因为字节序列可以无拷贝地共享：切片、拼接、传参都不必担心有人改坏共享的数据。所以任何"修改"都必须先生成新的字节——[]byte(s) 转换拿到的是可修改的副本，改它不动原串。

Go 的 string 不要求内容是合法 UTF-8，它能装任意字节。文本场景约定按 UTF-8 解释，所以才有"码点"这层视图。

go
s := "Go语言"
fmt.Printf("%T %v\n", s[0], s[0]) // uint8 71：'G' 的字节值
fmt.Println(s[2])                 // 232：'语' 的第一个字节，不是"语"

索引给到的永远是一个字节，哪怕那个位置"看起来"是一个汉字的开头。

2. range 按码点走，索引按字节走

for i, r := range s 每次解码一个 UTF-8 码点（rune，即 int32），但 i 报告的是这个码点在原串中的字节起点。为什么 i 不报"第几个码点"？因为解码是顺着字节流走的，记录字节偏移成本为零，而"第几个"要额外计数——语言选择了更贴近底层事实的那个。

于是截断中文不能按字节切：s[:4] 会把 语 切成半个，得到非法 UTF-8。要在码点层面操作，先转 []rune：

go
runes := []rune(s)        // 每个元素一个码点，与字节布局无关
head := string(runes[:3]) // "Go语"

[]byte 与 []rune 两种转换回答两个不同的问题：前者拿到原始字节（算长度、写协议、处理二进制），后者拿到码点序列（数"字"、按字符截断）。两种转换各有一次复制成本；纯 ASCII 场景 len 就是码点数，不必转。

两个世界对照一遍，本篇的结论都在这张表里：

操作单位"Go语言" 上的结果
len(s)字节8
len([]rune(s))码点4
s[i]单个字节byte，如 s[2] 是 232
range s码点，下标是字节偏移偏移 0 1 2 5

3. Map 读零值安全，comma-ok 区分三种状态

map 的键经哈希函数映射到桶；读一个不存在的键，找到的是空位，直接返回值类型的零值。为什么读不 panic？因为"缺失 → 零值"是语言约定的确定性行为，m[k]++ 这类累加才无需先判断存在。

但零值抹掉了"存在"的信息：m["book"] == 0 分不清"没这本书"和"库存为零"。comma-ok 把两件事拆开：

go
v, ok := m["book"] // ok=false：键不存在；ok=true：存在，v 可能仍是 0

"值为零""键不存在""已 delete"是三种不同状态，业务上要区分就得用 ok，不能靠猜值。

go
m["go"]++ // 读、加、写三步：缺失时命中"零值"约定，不需要先判断存在

这一行能工作，靠的正是开头那条"缺失 → 零值"的约定；也正因为它是读改写三步的组合，它不是一次原子操作。

4. 写入会扩容，遍历顺序不可依赖，nil 不能写

写入先查键是否存在：存在则覆盖，不存在则插入；桶装不下时扩容——分配更多桶、搬迁旧数据。这些布局细节语言规范一概不承诺，于是遍历顺序也没有承诺，而且运行时故意随机化每次遍历的起点，避免有人碰巧依赖它。

需要稳定的输出顺序，就先把键收集出来排序：

go
keys := make([]string, 0, len(m))
for k := range m { keys = append(keys, k) }
sort.Strings(keys)
for _, k := range keys { fmt.Println(k, m[k]) }
go
delete(m, "not-exist") // 删除不存在的键：什么也不做，不 panic

delete 和读取一样宽容：它操作的是键的存在性，不存在就无事可做。会 panic 的只有写入。

另一头是 nil map：var m map[string]int 声明了一个空指针。读它安全（空表，全部返回零值）、len 为 0、delete 也不报错；但写入没有可用的存储，直接 panic。为什么读安全写不安全？读不需要存储，写必须先有表——所以用 map 前要么 make，要么字面量初始化。

04 · 接口是谁定义的

一句话模型：接口不是实现类要遵守的清单，而是调用方对能力的最小描述；实现关系由方法集合隐式满足。

先看一个现象

一个读取函数只写出它要的能力：

go
func readAll(r io.Reader) (string, error) { /* ... */ }

readAll(strings.NewReader("go")) // 可以
readAll(bytes.NewBufferString("go")) // 也可以

你以为：一个类型要先声明"我实现 io.Reader"，才能传进去。实际：io.Reader 的全部内容只有一行 Read(p []byte) (int, error)，谁的方法集合里有这个方法，谁就能进来——strings.Reader 和 bytes.Buffer 都没有 import 这个接口，更没有写 implements。

场景换成写入也一样。如果签名写死具体类型，测试替身永远进不来：

go
func save(b *bytes.Buffer) error { /* ... */ } // 写法一
// 或者：
func save(w io.Writer) error { /* ... */ }     // 写法二

第一行要求调用方交出 bytes.Buffer；第二行只要交出"能写字节的东西"，bytes.Buffer、文件、以及自己写的一个只有 Write 方法的假对象都能进来。接口把"谁能被调用"的决定权，从实现方挪到了调用方手里。

再看一个别扭的地方：bytes.Buffer 有几十个方法，readAll 却只能看到 Read。接口不是给对象贴的类别标签，而是调用方拿起对象时戴的一副手套：只露出需要的那根手指。

先建立直觉

右半边那两格是本篇最容易被忽略的事实：接口变量从来不是"一个对象"，而是"类型 + 值"的一对信息。后文所有关于 nil 的结论都从这两格推出来。

机制拆成四步

1. 接口写在调用方，描述"我需要什么"

为什么由调用方定义？因为需求掌握在调用方手里：我只要"能读出字节"，就不该要求对方连 Write、Seek、Close 都实现。小接口让测试替身只写一个方法，也让标准库里原本毫不相干的类型直接可用。依赖方向因此倒过来：实现方不需要知道接口存在。

对比两种宽度，差别不在语法，而在谁有资格进来：

go
type Writer interface { Write(p []byte) (int, error) } // 一个方法

type WriterPlus interface {
    Write(p []byte) (int, error)
    Flush() error
    Close() error
    Name() string
}

WriterPlus 逼着测试替身写四个方法，其中三个与"写入"无关；Writer 只要求一个。接口每多一个方法，能进来的实现就少一批。

这不是绝对规则。跨包公共契约（比如 io.Reader）适合集中定义，所有人才能复用同一个名字。判断标准始终是：这个接口是否准确表达了需求，它的变化会不会波及无关实现。

2. 满足关系是方法集合的隐式匹配

Go 没有 implements 关键字。编译器在赋值或传参那一刻检查：右侧类型的方法集合是否包含接口要求的方法，签名逐个一致就通过。

为什么错误出现在调用处，而不是类型定义处？因为"满足哪些接口"不是类型的固有属性——一个类型可以同时满足 Reader 和 Writer，也能被将来新写的接口满足。这里要记一条方法集合规则：T 的值方法集合只含值接收者方法，*T 才同时拥有值接收者和指针接收者方法。所以一个只用指针接收者定义 Read 的类型，T{} 传不进去，&T{} 可以。

go
type OnlyPtr struct{}
func (o *OnlyPtr) Read(p []byte) (int, error) { return 0, io.EOF }

var bad Reader = OnlyPtr{}  // 编译失败：值方法集合不含 Read
var ok  Reader = &OnlyPtr{} // 通过：指针方法集合含 Read

报错位置是这两行赋值，不是 OnlyPtr 的定义处——同一个类型换个接口，结论可能完全不同。

3. 接口变量里装的是（动态类型，动态值）

把 bytes.Buffer 传给 Reader，接口拿到的是"当前类型 *bytes.Buffer + 当前值"这一对信息。为什么必须有类型？接口变量的静态类型只有 Reader，运行时得知道具体是谁，才能把 Read 分派到正确的方法体。为什么必须有值？方法需要接收者。

于是接口调用是一次运行时分派，而不是编译期写死的地址。这也接上了上一篇：装进接口的是值的副本；如果那个值本身是指针，复制的只是指针，底层对象并没有被复制。接口没有改变 Go 的值语义。

go
bb := bytes.NewBufferString("go")
var r Reader = bb  // r 里：类型 *bytes.Buffer，值是 bb 这个指针的副本
bb.Reset()         // 底层对象被改，r 下一次 Read 看到的是新内容

r 持有的是指针副本，不是 Buffer 的副本——这一点和上一篇的 t := s 是同一个道理。

4. typed nil：为什么 boxed == nil 是 false

go
var buf *bytes.Buffer
var r Reader = buf
// buf == nil → true，r == nil → false

为什么？nil 接口要求"类型和值都为空"，而 r 的类型栏写着 *bytes.Buffer，只空了值栏。此时调用 r.Read(...)，方法体解引用空指针就会 panic——接口看起来能用，其实是个空壳。

怎么处理？在构造边界就杜绝：创建失败时直接返回 nil 接口，而不是把失败的具体指针升级成接口。若某个实现确实支持 nil 接收者，要显式写明并测试，别假设所有实现都遵循同一约定。

把三栏摆在一起看更清楚：

写法动态类型动态值== nil
var r Reader空空true
var b *bytes.Buffer; var r Reader = b*bytes.Buffernilfalse
var r Reader = bytes.NewBufferString("go")*bytes.Buffer非 nil 指针false

== nil 只能识别第一行。第二行是"有类型、没值"，第三行是"有类型、有值"。

	"bytes"
	"fmt"
	"io"
	"strings"
)

// 可调参数

	// 传给最小 Reader 的内容
	inputText = "go interface"

	maxRead = 4
)

// Reader 是调用方定义的最小接口：只要一个方法。
type Reader interface {
	Read(p []byte) (int, error)
}

func readAll(r Reader) (string, error) {
	var out strings.Builder
	buf := make([]byte, maxRead)
	for {
		n, err := r.Read(buf)
		out.Write(buf[:n])
		if err == io.EOF {
			return out.String(), nil
		}
		if err != nil {
			return out.String(), err
		}
	}
}

func main() {
	sr := strings.NewReader(inputText)
	got, err := readAll(sr)
	fmt.Printf("strings.Reader → %q  err=%v\n", got, err)

	bb := bytes.NewBufferString(inputText)
	got, err = readAll(bb)
	fmt.Printf("bytes.Buffer   → %q  err=%v\n", got, err)

	// typed nil：这里只判定，不调用 Read（调用会 panic）
	var nilBuf *bytes.Buffer
	var boxed Reader = nilBuf
	fmt.Printf("nilBuf == nil  ? %v\n", nilBuf == nil)
	fmt.Printf("boxed  == nil  ? %v\n", boxed == nil)
	fmt.Printf("boxed 的动态类型：%T\n", boxed)

	// 对照：真正的 nil 接口
	var empty Reader
	fmt.Printf("empty  == nil  ? %v\n", empty == nil)
}

05 · 失败是值，不是意外

一句话模型：Go 把失败作为返回值，是为了让失败成为调用者必须处理的普通数据；%w 把一次失败变成可追溯的链。

先看一个现象

go
_, err := loadUser(404)
fmt.Printf("%v\n", err)
// handler: fetch: id=404: lookup id=404 kind=missing: not found
fmt.Println(errors.Is(err, ErrNotFound)) // true

你以为：加了几层上下文，原始错误就被"换成"一个新错误了。实际：%w 把原因挂在新的错误值上，形成一条链；文本变长了，但 errors.Is 仍能沿着链找到最底下的哨兵。同一个失败，上层看到的是上下文，下层判定的是原因——这两件事可以同时成立。

再看一个反例：把代码里的 %w 改成 %v，文本一个字不变，errors.Is 却变成 false。说明被判定的是那条链，不是那串字。

go
cause := errors.New("disk full")
wrapped := fmt.Errorf("write: %w", cause)
flat    := fmt.Errorf("write: %v", cause)

fmt.Println(wrapped.Error() == flat.Error()) // true：文本一样
fmt.Println(errors.Is(wrapped, cause))       // true
fmt.Println(errors.Is(flat, cause))          // false：链断了

两个错误打印出来都是 write: disk full，调用者却只有其中一个能追问原因。差别藏在值里面，不在文本里。

先建立直觉

图里"返回值"和"链"是同一件事的两个视角：返回值负责把失败送到调用者，链负责让调用者在不破坏上下文的前提下追问原因。

机制拆成五步

1. 失败占据一个返回值位置

函数签名把失败写成第二个结果，调用者不接它就拿不到正常结果。为什么不用异常？因为异常会让失败从正常控制流里消失：函数签名看不出会失败，调用处也看不出该处理什么。if err != nil 只是一个普通分支，编译器不会替你跳过它。

对照 panic 的用途：panic 留给"程序不该继续"的 bug，比如不该发生的索引越界；"ID 没查到""输入格式不对"是可预期失败，应该走返回值。把预期失败写成 panic，等于把恢复责任推给最外层，还让中间层无法就地决策。

go
func divide(a, b int) (int, error) {
    if b == 0 { return 0, errors.New("divisor is zero") }
    return a / b, nil
}

签名本身就是文档：调用者看到两个返回值，就知道第二个需要检查。若改成 panic("divisor is zero")，签名里什么也看不出来，调用者只能靠读实现或靠运行时崩溃才发现问题。

2. 哨兵错误：用 errors.Is 而不是字符串比较

错误文本是给人看的，改个措辞判定就崩。哨兵是包级可比较的错误值，比如 var ErrNotFound = errors.New("not found")。errors.Is(err, ErrNotFound) 会沿 Unwrap 链逐个比较，因此包装之后依然能回答"是哪一类失败"。

为什么不直接 err == ErrNotFound？只在确定没有包装、且动态类型可比较时它才成立；一旦经过 %w，比较就失败。errors.Is 还兼容自定义了 Is(error) bool 的类型，统一用它更稳。

go
var ErrNotFound = errors.New("not found")
err := fmt.Errorf("load user: %w", ErrNotFound)
fmt.Println(err == ErrNotFound)          // false：已经不是同一个值
fmt.Println(errors.Is(err, ErrNotFound)) // true：链上还有它

3. %w 建立链，%v 只留下文本

fmt.Errorf("fetch: %w", err) 生成一个带 Unwrap() error 的包装错误，原错误对象仍挂在链上；fmt.Errorf("fetch: %v", err) 只是把原因格式化成字符串，原对象被丢弃，Is 和 As 再也走不下去。

为什么需要区分？因为"给错误加上下文"和"保留错误身份"是两件事： %v 只做了前者，%w 两件都做。判断一个包装是否可逆，看它有没有 Unwrap 就够了。

go
wrapped := fmt.Errorf("load: %w", cause) // 有 Unwrap()，指向 cause
flat    := fmt.Errorf("load: %v", cause) // 只有格式化后的字符串

包装还可以继续叠加：每一层 %w 都在链上再挂一节，文本前缀逐层加长，链却始终连着最底下的原因。

4. errors.As 取回结构化错误

Is 只能回答"是不是这一类"。要读具体字段——比如某个具体错误的 ID、Path——就得用 errors.As：它沿链找第一个可赋值给目标类型的错误，把它写回目标变量。

目标必须是指针的指针：

go
var le *LookupError
if errors.As(err, &le) { fmt.Println(le.ID) }

为什么多一层 &？因为 As 要修改调用者的变量，参数得是"指向 *LookupError 的指针"。直接传 le 不仅写不回去，还会 panic。

两个判定函数分工明确：

想问的问题用什么第二个参数命中后得到什么
"是不是这一类失败"errors.Is一个错误值，如 ErrNotFoundtrue / false
"要读具体字段"errors.As指针的指针，如 &letrue，le 被赋值

5. defer 让失败路径也完成清理

多返回值加 if err != nil { return }，让一个函数有很多个出口。把 Close() 交给 defer，就等于把清理绑在"函数退出"，而不是绑在某一条 return 上——成功和失败都执行。

一个细节：defer 按后进先出执行。如果想在清理后观察状态，观察用的 defer 要先注册，Close 的 defer 后注册，这样 Close 先跑，观察者才看得到已关闭的状态。

go
rc := &tracingCloser{}
defer func() { fmt.Println("观察：closed =", rc.closed) }() // 先注册，后执行
defer rc.Close()                                          // 后注册，先执行

反过来注册，观察者就会看到 closed=false——不是清理没发生，而是它发生得更晚。demo 里的 Close() 自己打印了一行，所以这行出现在 main 的所有输出之前：loadUser 一返回，defer 就执行了。

06 · defer 到底什么时候执行

一句话模型：defer 在函数返回路径上按 LIFO 执行，参数在 defer 语句处求值；panic 是沿调用栈展开的紧急退出，recover 只能在 defer 里接住。

先看一个现象

同一个变量，两种 defer 写法，答案不同：

go
func demo() {
	i := 42
	defer fmt.Println("A:", i) // 打印 A: 42
	i = 99
	defer func() { fmt.Println("B:", i) }() // 打印 B: 99
}

A 后注册却后执行（B 先打印），而且 A 打印的是注册时的旧值 42。你以为 defer 是"离开这段代码时执行、执行时再取变量"；实际它挂在整个函数的返回路径上，按后进先出执行，并且参数在 defer 语句那一行就求值固定了。

panic 的行为更像意外：

go
func risky() {
	defer fmt.Println("defer 仍然执行")
	panic("boom")
	fmt.Println("到不了这里")
}

panic 让"到不了这里"永远不执行，但已经注册的 defer 照常跑——panic 不是"跳过一切"，而是"换一条退出路径"，原来注册的清理还在路径上。

先建立直觉

两半边共享同一个机制：defer 是函数退出时唯一还会执行的代码。正常返回靠它收尾，panic 展开也靠它收尾——所以 recover 必须长在 defer 里。

机制拆成四步

1. defer 挂在函数上，不在代码块上

defer f() 把调用登记到当前函数的延迟列表，函数返回（或 panic 展开）时按注册的逆序执行。为什么是逆序？因为资源获取与释放天然对称嵌套：后打开的连接先关、内层的锁先解，LIFO 正好匹配。为什么不在 if 或循环结束时执行？因为 defer 的作用域就是函数——这也是循环里注册的 defer 要等整个函数返回才跑的原因，循环体不是函数。

go
func paired() {
	defer fmt.Println("清理 1（先注册）")
	defer fmt.Println("清理 2（后注册）")
	fmt.Println("主体")
	// 输出：主体 → 清理 2 → 清理 1
}

先注册的离资源远、后注册的离资源近，逆序弹出正好从最内层开始收尾。

2. 参数在 defer 语句处求值

defer fmt.Println(i) 是一次完整的函数调用，只是执行被推迟：实参 i 在这一行就求值并复制，之后 i 怎么变都与它无关。而 defer func() { fmt.Println(i) }() 推迟的是一个闭包，闭包体在执行时才去读 i，读到的是当时的值。

两种写法都对，区别只在"冻结什么"：想快照就传参，想看最终值就闭包捕获。判断口诀：看到 defer 先问"实参什么时候算"，再问"闭包体什么时候读"。

go
for i := 0; i < 3; i++ {
	defer fmt.Printf("%d ", i) // 实参当场求值：函数退出时输出 2 1 0
}

闭包版本在 Go 1.22 之后每轮循环变量互相独立，但规则没有变：闭包体执行时才读，读到的是执行那一刻的值。

3. return 不是原子操作，defer 可以改写返回值

return x 实际分两步：先把 x 写入返回值，再执行 defer，最后真正返回。只有命名返回值能让 defer 摸到返回值——它有名字，defer 闭包里可以直接赋值：

go
func run() (err error) {
	defer func() { err = fmt.Errorf("recovered: %v", recover()) }()
	panic("boom") // err 被改写成接住的内容，调用者拿到 error 而不是崩溃
}

匿名返回值是复制到栈上的临时量，defer 改不到。所以"defer 修改返回值"不是 defer 自带的属性，而是命名返回值提供的入口。反例看匿名返回值：defer 只能改到自己的局部变量：

go
func anon() string {
	s := "结果"
	defer func() { s += "！" }() // 改的是局部变量 s
	return s                     // 返回 "结果"，感叹号丢了
}

4. panic 展开，recover 在 defer 里拦截

panic 立即停止当前函数的正常控制流，然后沿调用栈逐层展开；每一层的 defer 照常执行——这正是资源清理仍然有效的原因。某一层 defer 中直接调用 recover() 并拿到非 nil 值，展开就地停止，包含这个 defer 的函数带着它的修改（比如改过的命名返回值）正常返回，调用者继续运行。若没有任何 recover，展开到栈底，程序打印 panic 值与堆栈后退出。

为什么 recover 必须写在 defer 里？panic 发生后，普通代码已经不在执行路径上，唯一还会被调用的就是 defer；放在任何普通位置都捕不到。另外 recover 只作用于当前 goroutine：

go
go func() {
	defer func() { recover() }() // 每个 goroutine 要有自己的拦截点
	panic("worker boom")
}()

main 里的任何 recover 都救不了这个 goroutine——展开只沿它自己的栈走。

07 · 并发不是多开线程

一句话模型：Goroutine 是可被调度器暂停的 continuation，Channel 不是管道而是"谁先走"的同步协议。

先看一个现象

go
ch := make(chan int)
ch <- 1
fmt.Println(<-ch)

你以为 1 被存进了 ch，下一行会打印出来。实际程序永久卡在第一行，运行时最终报 all goroutines are asleep - deadlock!。

再看一个更短的：

go
go func() { fmt.Println("finished") }()

你以为"新开一条线程，它马上打印 finished"。实际这一行可能什么都不打印——main 一返回，整个程序就结束了，那个 Goroutine 还没轮到执行。

两个现象指向同一件事：go f() 不是"开一条线程立刻跑"，而是"把一个可以暂停、之后接着跑的执行流交给调度器"；ch <- 1 也不是"往管子里塞东西"，而是"和接收方约定谁先走"。把这两件事当成线程和管道，后面所有阻塞、死锁、泄漏都会变得不可解释。

还有一个容易被忽略的对照：把 runtime.GOMAXPROCS(1) 写进程序，1000 个 goroutine 照样能创建、照样能全部跑完，只是同一时刻只有一个在执行。你以为"有 1000 个 goroutine 就是 1000 路并行"，实际 goroutine 的数量描述的是"有多少件事被组织成可并发推进"，并行度由 P 的数量和 CPU 核心共同决定。并发是组织方式，并行是执行状态——这是"并发不是多开线程"的另一半意思。

先建立直觉

图里两个阻塞点长得不一样：无缓冲是"对方没到"，有缓冲是"格子满了"。分清这两种等待，才能解释为什么同一段代码只改一个容量参数就从死锁变成通畅。

机制拆成四步

1. go f() 创建的是 continuation，不是线程

Goroutine（简称 G）是一次函数调用连同它的栈、程序计数器等状态。调度器可以在某个点把它暂停，保存现场，过一会儿再恢复继续执行——这种"能被暂停并恢复的执行流"叫 continuation。

为什么 go f() 返回后 f 不一定开始执行？因为这个语句只完成"创建 G 并放入可运行队列"，不承诺立刻执行。当前 Goroutine 不主动让出、不阻塞，新 G 就可能一直排队；如果 main 在此期间返回，程序直接退出，队列里剩下的 G 全部作废。

为什么 Goroutine 可以开成千上万个？它的初始栈很小且能按需增长，创建和切换都由 Go 运行时在用户态完成，不需要为每个任务向操作系统申请线程。但"轻量"不等于"免费"：每个 G 仍占内存和调度项，没有退出条件的后台循环照样泄漏。启动一个 G 之前，就要想清楚谁让它停。

一个最小但完整的生命周期长这样：

go
var wg sync.WaitGroup
wg.Add(1)
go func() {
    defer wg.Done() // 函数返回时通知等待方
    work()
}()
wg.Wait()

wg.Add(1) 必须放在 go 之前：否则 goroutine 可能先执行完 Done() 让计数器提前归零，Wait() 就失去意义。这里真正兑现"等它跑完"承诺的是 wg.Wait()，go 语句本身什么都不保证。

2. G-M-P：谁真正在跑代码

三个角色要分开记：

  • M（Machine）：操作系统线程，唯一真正执行 Go 代码的角色。
  • P（Processor）：逻辑处理器，持有本地可运行队列和执行上下文。
  • G（Goroutine）：被调度的最小执行流单位。

M 必须绑定一个 P，才能从队列里取 G 来执行。为什么多这一层 P？如果所有 M 都去同一个全局队列抢 G，每次取任务都要争一把锁；每个 P 有自己的本地队列，取任务大多不用抢，调度成本才压得住。

runtime.GOMAXPROCS(n) 改的是 P 的数量，也就是"同时执行 Go 代码的上下文最多几个"，不是"最多只能有 n 个 Goroutine"。设置成 2 之后，1000 个 G 照样存在，只是同时最多 2 个在跑，其余排队或等待。

go
previous := runtime.GOMAXPROCS(2)
defer runtime.GOMAXPROCS(previous) // 库代码里改完要恢复，别影响同进程其它任务

GOMAXPROCS 是进程级设置。把它从 1 调大，只给"CPU 密集且能拆分"的任务带来更多并行机会；任务本来就串行、瓶颈在 I/O 或下游服务时，调大它不会缩短总耗时。判断有没有真并行要看执行状态，不要数 goroutine 个数。

为什么在某个 G 上阻塞不会拖垮整个程序？G 因为 channel、锁而阻塞时会被挂起，M 与 P 解绑，P 换一个可运行的 G 继续跑。所以"一个 goroutine 卡住了"和"程序卡住了"不是一回事——除非所有 G 都卡住，才会触发开头那个 deadlock 报告。

3. 无缓冲 channel：阻塞点是"对方就绪"

make(chan int) 得到无缓冲 channel，它没有存放值的槽位。于是：

  • ch <- v 完成的时刻，不是"v 被放进了某处"，而是"某个接收方已经把它接走"；
  • <-ch 完成的时刻，也不是"从某处取出了值"，而是"某个发送方正好把它递过来"。

为什么开头的三行一定死锁？同一个 G 执行到 ch <- 1 时卡住，它自己后面的 <-ch 永远没有机会执行；程序里又没有别的 G 能来接收。双方（其实是同一个 G 的两半）互相等，运行时发现所有 G 都睡着，只能报 deadlock。

select 加 time.After 为什么能破局？因为它给等待加了一条别的出路：时间到，超时分支就绪，select 就走那条路，程序可以打印、清理、退出。注意这不是"接收成功"，只是"不等了"——Demo 里随后会补一个真正的接收，让卡住的发送方完成并正常退出。

4. 缓冲 channel：改的是就绪条件，不是取消协议

make(chan int, 1) 多出一格缓冲区：

  • 只要缓冲区有空位，ch <- v 就立即完成，发送方不必等接收方出现；
  • 只要缓冲区里有值，<-ch 就立即完成，接收方不必等发送方出现。

为什么缓冲不能消除阻塞？格子里已经有一个值、又没人来取时，第二次发送依然要等。缓冲只回答一个问题：下游暂时不接收时，上游最多能暂存多少？ 它是有限货架，不是无限管道。

所以容量参数改变的是"什么条件下可以继续走"，而不是"要不要遵守同步协议"。把容量开得很大，只会积压更多在途数据、拉长排队延迟。真正该问的始终是：如果对方一直不来，我这一个 G 会不会永远停在原地？

你的问题选哪种做法
"对方必须已经拿到，我才继续"无缓冲：交接本身就是同步点
"对方慢点没关系，但最多攒 N 个"缓冲 N：先暂存，满了再等
"我等多久就放弃"配 select + time.After 或取消信号

这张表不是 API 字典，而是三个决策问题：要不要面对面交接、能暂存多少、等多久放弃。

package main

import (
	"fmt"
	"time"
)

const (
	waitLimit   = 50 * time.Millisecond // 可调参数：等待发送就绪的上限，改大只改变等待时长
	bufferedCap = 1                     // 可调参数：缓冲格数，改成 0 会复现无缓冲的阻塞
)

func main() {
	fmt.Println("[阶段A] 无缓冲 channel：先发，再收")

	unbuffered := make(chan int)
	sent := make(chan struct{})
	go func() {
		unbuffered <- 7
		close(sent)
	}()

	// 没有接收方，发送永远不就绪；超时分支给出等待上界，避免死锁。
	select {
	case <-sent:
		fmt.Println("[阶段A] 发送已就绪（按本 demo 的结构不会发生）")
	case <-time.After(waitLimit):
		fmt.Println("[阶段A] 发送未就绪 → 超时退出，不是死锁")
	}

	// 补上接收，让阻塞的发送方完成，goroutine 正常退出。
	fmt.Printf("[阶段A] 补一个接收，收到 %d\n", <-unbuffered)

	fmt.Println("[阶段B] 缓冲 channel：先发，再收")
	buffered := make(chan int, bufferedCap)
	buffered <- 7
	fmt.Printf("[阶段B] 发送完成，缓冲区长度 %d\n", len(buffered))
	fmt.Printf("[阶段B] 收到 %d，缓冲区长度 %d\n", <-buffered, len(buffered))
}

08 · 取消是通知，不是命令

一句话模型：Context 只关闭一条叫 Done 的通道来广播"请停止"，真正停下必须靠被调代码自己在 select 或检查点响应。

先看一个现象

调用方准备好了取消，worker 却收不到：

go
ctx, cancel := context.WithCancel(context.Background())
go func() {
    for {
        work() // 循环里没有任何地方读 ctx
    }
}()
cancel() // 只关闭 ctx.Done()，不会中断 work()

你以为 cancel() 一调用，那个 goroutine 就被"叫停"了。实际它继续跑：循环里没有 ctx 的任何位置，信号发出去无人接收。

再看一个看似正确的 select：

go
select {
case <-ctx.Done():
    return ctx.Err()
case result := <-results:
    return result, nil
}

你以为"取消优先"，只要 Done 关闭就立刻退出。实际当 results 里也有值、两个 case 同时就绪时，select 随机挑一个——取消不是高优先级命令，只是"又一条就绪的路"。

两段代码合起来说明一件事：Context 不拥有停止 goroutine 的权力。它只做一件很小的事——关闭 Done() 通道。剩下的，全靠被调代码配合。

先建立直觉

图上最关键的一点：关闭只发生在父节点，观察发生在每个 worker 自己身上。 取消传的是信号，不是执行力。

机制拆成四步

1. Context 是一棵可取消的树

context.WithCancel(parent) 从父 ctx 派生子 ctx，并返回一个 cancel 函数；WithTimeout、WithDeadline 也一样，只是额外挂了一个定时器。每个子 ctx 记住自己的父节点，父节点取消时把信号沿树往下传。

为什么需要树？一个请求常常扇出多路工作：查缓存、调下游、写日志。你想让"客户端断开"这一件事同时停掉所有分支，树结构让你只取消根节点，所有分支的 Done 都会关闭。

go
parent, cancelParent := context.WithCancel(context.Background())
child, cancelChild := context.WithTimeout(parent, 2*time.Second)
defer cancelParent()
defer cancelChild()

注意取消不反向传播：cancelChild() 只关闭 child 的 Done，parent 和兄弟节点毫无感觉。子节点也不能把截止时间"延长"：WithTimeout(parent, 2s) 在 parent 只剩 200ms 时，实际 200ms 就到头了。

2. Done() 是一条"只关闭、不发送"的通道

ctx.Done() 返回 <-chan struct{}。取消时运行时做的事是 close(done)，不是 done <- struct{}{}。

为什么用关闭？因为关闭天然是对所有接收者的广播：任何正在 <-ctx.Done() 等待的 goroutine 都立刻得到零值并往下走；已经关闭的通道在 select 里永远就绪。若改成发送一个值，你还得先知道有多少个监听者，而且没人接听时发送会阻塞——那就不叫广播了。

配套方法各回答一个问题：

  • Done()：该停了吗（通道关闭即"是"）。
  • Err()：为什么停（context.Canceled 或 context.DeadlineExceeded）。
  • Deadline() / Value()：截止时间与请求元数据（本篇不展开）。

Err() 在取消之后稳定返回同一个错误，重复调用结果一致，所以判断时直接用 errors.Is(err, context.Canceled) 即可。

3. 停下是被调代码的协作义务

Go 没有"杀掉一个 goroutine"的 API。为什么？强制终止会跳过 defer、留下没释放的锁和写了一半的状态，比让任务自己收尾危险得多。所以 Go 选择协作式取消：通知发出后，被调代码在合适的点自己退出。

worker 的标准形状，是在阻塞点把 Done 放进 select：

go
select {
case n := <-jobs:
    handle(n)
case <-ctx.Done():
    return ctx.Err()
}

纯计算循环没有阻塞点，就自己加检查点：

go
for i, v := range values {
    if i%1000 == 0 {
        if err := ctx.Err(); err != nil {
            return err
        }
    }
    process(v)
}

为什么不是每次都查 Err()？检查本身有成本，分段检查是"响应及时"和"开销可控"之间的折中。关键是别让一段不可中断的工作长到用户已经走了你还在算。

4. WithTimeout 只是"定时器到点自动调用 cancel"

context.WithTimeout(parent, d) 相当于在 d 之后自动调用 cancel，所以 worker 那边完全不用改：还是监听同一个 Done。区别只在 Err()：手动 cancel() 得到 context.Canceled，超时自动触发得到 context.DeadlineExceeded。

go
ctx, cancel := context.WithTimeout(context.Background(), timeout)
defer cancel() // 提前完成时释放定时器与父子关联，必须写

为什么提前成功还要 defer cancel()？因为定时器还在跑、子 ctx 还挂在父节点的表里；不调用 cancel()，这些资源要等超时那一刻才释放。短请求反复这么做，累积的就是实实在在的泄漏。

最后一条边界：取消不保证优先。如果 Done 和数据同时就绪，select 可能先处理数据。业务上要求"取消后不再处理新任务"，就在使用数据前再查一次 ctx.Err()——判断发生在哪里，优先权就在哪里。

动手验证

动手验证取消一次，看 worker 怎么退出

先预测：主 goroutine 调 cancel() 之后，worker 会立刻停止吗？

运行：cd examples/minimal/08-context-cancel && go run .（标有「可调参数」的常量就是旋钮）

go
package main

import (
	"context"
	"fmt"
	"time"
)

const (
	workTicks = 3                     // 可调参数：手动取消前处理的任务数
	timeout   = 30 * time.Millisecond // 可调参数：WithTimeout 的超时时长，改大只改变等待时长
)

func worker(name string, ctx context.Context, jobs <-chan int, done chan<- string) {
	for {
		select {
		case n := <-jobs:
			fmt.Printf("[%s] 处理任务 %d\n", name, n)
		case <-ctx.Done():
			done <- fmt.Sprintf("[%s] 退出，原因：%v", name, ctx.Err())
			return
		}
	}
}

func main() {
	fmt.Println("[阶段A] 手动取消父 ctx，worker 监听子 ctx")

	parent, cancelParent := context.WithCancel(context.Background())
	defer cancelParent()
	child, cancelChild := context.WithCancel(parent)
	defer cancelChild()

	jobs := make(chan int)
	done := make(chan string, 1)
	go worker("worker-A", child, jobs, done)

	for i := 1; i <= workTicks; i++ {
		jobs <- i // 同步交接：send 返回时 worker 已经接走任务
	}
	cancelParent() // 父取消，子 ctx 的 Done 一并关闭
	fmt.Println(<-done)

	fmt.Println("[阶段B] WithTimeout 自动触发，无人调用 cancel")

	tctx, cancelTimeout := context.WithTimeout(context.Background(), timeout)
	defer cancelTimeout()
	jobsB := make(chan int)
	doneB := make(chan string, 1)
	go worker("worker-B", tctx, jobsB, doneB)

	fmt.Println(<-doneB) // 没有任务，worker 等到超时后从 Done 退出
}

输出里"处理任务"的行数等于 workTicks，把常量改大就多打印几行，但退出原因不变。这再次说明：停下的决定权在 worker 的 select 里，不在 cancel() 里。

容易误判的地方

  • cancel() 会终止 goroutine → 它只关闭 Done。worker 没有监听点就继续跑；context 包里没有任何"强杀" API。
  • 取消 case 比数据 case 优先 → select 同时就绪时随机挑一个。要求"取消后不开始新工作"，必须在使用数据前显式检查 ctx.Err()。
  • WithTimeout 之后可以省掉 defer cancel() → 不行。提前成功时定时器仍在跑、父子关联仍在，必须调用 cancel() 释放。

09 · 共享状态怎么才安全

一句话模型：两个 goroutine 同时访问同一变量且至少一个写，就必须建立 happens-before；Mutex 保护的是临界区，不是变量本身。

先看一个现象

8 个 goroutine 各给同一个计数器加 1000 次：

go
counter := 0
var wg sync.WaitGroup
for i := 0; i < 8; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for j := 0; j < 1000; j++ {
            counter++
        }
    }()
}
wg.Wait()
fmt.Println(counter) // 你以为 8000，实际常常小于 8000

你以为结果是 8000。实际输出往往是五千多、六千多，而且每次运行都可能不同；加上竞态检测器还会报 WARNING: DATA RACE。counter++ 看起来是一行代码，实际是"读旧值 → 加一 → 写回"三步，交错的goroutine 会从同一个旧值出发，写回两个一样的新值。

再看一个试图补救的写法：

go
mu.Lock()
tmp := counter
mu.Unlock()

mu.Lock()
counter = tmp + 1
mu.Unlock()

你以为"读和写都在锁里，安全了"。实际两个 goroutine 完全可能先后读到 0，再各自写回 1——两次访问确实各自被锁住了，但"读-改-写"这整件事被拆开，中间留出了缝隙。

先建立直觉

图上最该带走的一句话：竞态丢的是更新，不是时间。 两个 goroutine 都"执行了"加一，但其中一个的结果被另一个覆盖了，从最终数值上看那一次加法像是没发生过。

机制拆成四步

1. 三个条件同时满足才是数据竞态

  • 两个以上 goroutine 访问同一个变量；
  • 至少有一个访问是写；
  • 这些访问之间没有 happens-before 关系。

为什么全是读就安全？读不改状态，多个读者看到的值一致，互不干扰。为什么必须有第三条？因为"同时"不是指墙上时钟的同一纳秒，而是指"运行时无法证明这两个访问有先后"——只要证明不了，就按可能并发处理。

counter++ 为什么危险？它展开成 load、add、store 三条指令。G1 和 G2 的 load 都拿到 0，各自的 add 都得到 1，两次 store 都写回 1：两次加法只留下一个 1。这就是典型的丢失更新。

2. happens-before 不是时间先后，而是结果可见

说"A happens-before B"，意思是 A 的写入对 B 一定可见——B 不会读到 A 写入之前的值，更不会读到"写了一半"的值。它是 Go 内存模型给出的保证，不是我们对代码执行顺序的猜测。

常见的建立手段：

  • 同一个 goroutine 内的先后顺序；
  • channel 的发送 happens-before 对应的接收完成；
  • Mutex 的 Unlock() happens-before 随后的 Lock()；
  • WaitGroup 的 Done() happens-before 对应的 Wait() 返回。

为什么"代码写在前面"不算？因为编译器和 CPU 都会重排指令，另一个 goroutine 又没有任何同步点，它甚至可能永远看不到你的写入。同步不是"等一等"，而是在两条执行流之间建立一条可见性通道。

3. Mutex 保护的是临界区，不是变量

Lock() 与 Unlock() 之间的那段代码叫临界区；运行时保证同一时刻只有一个 goroutine 能进入。

go
mu.Lock()
counter++ // load + add + store 全在临界区内
mu.Unlock()

为什么必须把整段"读-改-写"圈进去？只锁写不锁读，读到的就是别人改之前的值；锁了每一步却在中间放开，别的 goroutine 就能插进来重演"都读到 0"。锁的单位是一段不允许被打断的逻辑，不是"对某个变量名的访问次数"。

为什么漏掉一次读也会出错？竞态是按"每一次访问"判定的。9 次访问进了临界区、1 次读裸奔，那 1 次就是竞态。判断标准是"这个变量还有没有没被同步覆盖的访问"，而不是"我有没有用过锁"。

通常写 defer mu.Unlock() 更安全，但注意 defer 要到函数返回才执行：临界区后面若还有长任务，锁会被持有到不该持有的时刻。那种情况就把临界区单独封成一个小函数。

4. 原子操作与 channel 各自的边界

sync/atomic 的 AddInt64(&n, 1) 把"读-改-写"做成一条不可分割的原子指令，比加锁轻。

为什么它不能包办一切？原子性只针对这一次操作。"先看 n 是否小于上限、再决定是否加一"这种复合逻辑，两步之间仍会被打断，需要 CAS 循环或锁；"账户 A 减 100、账户 B 加 100"这类多个变量的一致性，也不是单次原子操作能保证的。

channel 适合转移数据所有权：数据交出去之后，接收方负责，发送方不再碰。但发送指针不等于转移所有权——两个 goroutine 拿着同一个指针继续改对象，竞态照样存在，仍需新的同步协议。

场景合适的工具
单一计数器增减sync/atomic
多步复合逻辑、多个变量sync.Mutex
把数据交给另一个 goroutine 处理channel

动手验证无锁与加锁：同一段累加的两种结局

先预测：8 个 goroutine 各累加 1000 次，无锁结果会稳定等于 8000 吗？

运行：cd examples/minimal/09-shared-state && go run .（标有「可调参数」的常量就是旋钮）

go
package main

import (
	"fmt"
	"sync"
)

const (
	goroutineCount = 8    // 可调参数：并发 goroutine 数
	increments     = 1000 // 可调参数：每个 goroutine 的累加次数
)

func addUnlocked(counter *int, wg *sync.WaitGroup) {
	defer wg.Done()
	for i := 0; i < increments; i++ {
		*counter = *counter + 1 // 读-改-写 unprotected：结果不可依赖
	}
}

func addLocked(counter *int, mu *sync.Mutex, wg *sync.WaitGroup) {
	defer wg.Done()
	for i := 0; i < increments; i++ {
		mu.Lock()
		*counter = *counter + 1 // 整段读-改-写都在临界区内
		mu.Unlock()
	}
}

func main() {
	fmt.Printf("[阶段A] 无锁累加：%d 个 goroutine × %d 次\n", goroutineCount, increments)
	counter := 0
	var wg sync.WaitGroup
	wg.Add(goroutineCount)
	for i := 0; i < goroutineCount; i++ {
		go addUnlocked(&counter, &wg)
	}
	wg.Wait()
	fmt.Println("[阶段A] 结果不确定，因此不打印数值；用 go test -race 复核数据竞态")

	fmt.Println("[阶段B] Mutex 保护临界区：同样次数")
	counter = 0
	var wg2 sync.WaitGroup
	var mu sync.Mutex
	wg2.Add(goroutineCount)
	for i := 0; i < goroutineCount; i++ {
		go addLocked(&counter, &mu, &wg2)
	}
	wg2.Wait()
	want := goroutineCount * increments
	fmt.Printf("[阶段B] 期望 %d，实际 %d，一致：%v\n", want, counter, counter == want)
}

10 · 谁来等这些 goroutine

一句话模型：启动并发只是第一步，编排要回答"谁等谁、失败传给谁、泄漏怎么防"——WaitGroup 管汇合，channel 管接力，泄漏源于没人接收的阻塞。

先看一个现象

3 个 worker 各算一个结果，发到同一个 channel，主 goroutine 等它们都结束再取：

go
results := make(chan int)
var wg sync.WaitGroup
wg.Add(3)
for i := 0; i < 3; i++ {
    go func() {
        defer wg.Done()
        results <- i * i * i // 第一步：交结果
    }()
}
wg.Wait()              // 第二步：等全部结束
fmt.Println(<-results) // 第三步：取结果

你以为 wg.Wait() 会等 worker 干完活，然后顺利取到结果。实际程序死锁：worker 卡在 results <- ... 上，发送没人接收就完不成，完不成就到不了 defer wg.Done()，计数器永远不归零，Wait 永不返回。"等完成"和"收结果"这两步的先后不是随手写的——每一步单独看都对的代码，顺序错了合起来就是死锁。

先建立直觉

图上最该带走的一句话：汇合的完成依赖接力的畅通。 Done() 写在发送之后，"人都到齐"的前提是"货都送到了"；只要有一环阻塞且没人来解，整条编排就停在那里。

机制拆成四步

1. WaitGroup 只回答"这一批都结束了吗"

WaitGroup（完成计数器）只做一件事：Add(n) 登记尚未完成的任务数，每个任务结束时 Done() 交回一张，Wait() 等计数归零。

为什么 Add 必须写在 go 之前？Wait 判断的是"此刻还有多少没完成"；计数若在 goroutine 内部才加，Wait 可能在所有 Add 之前看到零，直接返回，等待形同虚设。为什么 Done 要写成 defer？函数无论从哪条路径返回都会交回计数，panic 也不例外；漏交一次，Wait 就永远等不齐。

同样要清楚它不管什么：不传结果、不传失败、不取消任务。计数归零只代表"都退出了"，不代表"都成功了"。

2. 结果走 channel：等数据是另一种"等"

fan-out/fan-in 是最常用的编排形状：主 goroutine 把任务发进 jobs channel，N 个 worker 领活，结果全部汇入同一个 results channel，主 goroutine 统一汇总。

go
go func() {
    wg.Wait()      // 所有 worker 退出之后
    close(results) // 不会再有人发送，关闭才安全
}()
for r := range results { // range 到 close 为止：这是"等数据"
    sum += r
}

为什么关闭要交给一个单独的协调 goroutine？多个 worker 都是发送者，谁都不能自己关——对已关闭的 channel 再 close 会直接 panic；而"所有发送者都结束"这个时刻，只有 wg.Wait() 知道。于是分工明确：WaitGroup 数人头，channel 传数据，等齐人头的那一方才有资格关闭。

3. 先等完再收，为什么死锁

回头看开头的现象：Done 排在发送之后，Wait 等的是 Done，而接收又排在 Wait 之后——接收永远开始不了，发送永远完不成，等待链绕成一个环。

解开只有两个方向，对应两种正确形态：

  • 让发送永不阻塞：results 的缓冲容量 ≥ 结果总数，worker 放下结果就能走到 Done，汇合照常完成，主 goroutine 事后再收。
  • 让接收与等待并行：main 一边 range results 一边收，协调 goroutine 负责 wg.Wait() 后关闭，收完 range 自然结束。

两种形态的共同点是打破环：不能让"接收的开始"依赖"汇合的完成"，而汇合又依赖"发送能完成"。

4. 泄漏：没人接收的阻塞

把一个值发给没有接收者的 channel：

go
orphan := make(chan int)
go func() { orphan <- 99 }() // 没人接收，这条 goroutine 永远停在这里

为什么程序不报 deadlock？运行时只在整个程序所有 goroutine 都睡死时才报警；这里 main 还活着、还在往下跑，那条卡住的 goroutine 就被静默遗忘——它的栈、闭包引用的变量全部无法释放。这就是 goroutine 泄漏：不崩溃，只积累，在长期运行的进程里慢慢吃掉内存。

防泄漏的办法是给每个阻塞点留出口：select 配上 time.After 或 ctx.Done()，等待就有了"不等了"的分支。启动任何 goroutine 之前先问一句：它的每一步阻塞，谁负责解除？答不上来，就是在攒一个未来的泄漏。

5. 失败传给谁

worker 会出错，而错误和结果一样需要明确的接收方。最直接的做法是让结果自带错误字段，随同一个 channel 汇入：

go
type result struct {
    val int
    err error // worker 把失败交给编排者，而不是自己打印了事
}

为什么不让 worker 自己处理失败？重试、跳过还是整体放弃，是"等待的那一方"才能做的决策——它看得见全局进度，单个 worker 看不见。错误塞进结果 channel 之后，编排者收到部分结果加一个错误时，必须当作"未完整完成"处理，不能当成全量成功。

你要等的用什么等
一批工作全部退出WaitGroup：Add / Done / Wait
数据流自然结束range 到 close
不能等太久select + time.After / ctx.Done

动手验证fan-out/fan-in 汇合与一条被保护的发送

先预测：阶段 A 的 results 若改成无缓冲，这个程序还能跑完吗？

运行：cd examples/minimal/10-orchestration && go run .（标有「可调参数」的常量就是旋钮）

go
package main

import (
	"fmt"
	"sync"
	"time"
)

const (
	workerCount  = 3                     // 可调参数：worker 数量，改成 1 或 8，汇总结果应当不变
	abandonAfter = 50 * time.Millisecond // 可调参数：无人接收时等多久放弃
)

func main() {
	fmt.Println("[阶段A] fan-out / fan-in：N 个 worker，一个结果 channel")

	const jobCount = 8
	jobs := make(chan int)
	results := make(chan int, jobCount) // 缓冲 = 结果总数：worker 发送不阻塞，能走到 Done

	var wg sync.WaitGroup
	wg.Add(workerCount) // Add 在 go 之前：等待方要先看到未完成计数
	for i := 0; i < workerCount; i++ {
		go func() {
			defer wg.Done() // defer：无论哪条路径返回都交回计数
			for job := range jobs {
				results <- job * job // 接力：算完就交给结果 channel
			}
		}()
	}

	// 关闭责任：所有发送者都结束之后才轮到 close，这里交给协调 goroutine。
	go func() {
		wg.Wait()
		close(results)
	}()

	for job := 1; job <= jobCount; job++ {
		jobs <- job
	}
	close(jobs) // 任务发完，worker 的 range 才会结束

	sum, count := 0, 0
	for r := range results { // 等数据的另一种形式：range 到 close 为止
		sum += r
		count++
	}
	fmt.Printf("[阶段A] %d 个 worker 汇合完成，收到 %d 个结果，总和 %d\n", workerCount, count, sum)

	fmt.Println("[阶段B] 没有接收者的发送：给等待留一个出口")
	orphan := make(chan int)
	go func() {
		select {
		case orphan <- 99: // 没有接收方，这个分支永远不会就绪
			fmt.Println("[阶段B] 发送成功（按本 demo 的结构不会发生）")
		case <-time.After(abandonAfter):
			fmt.Println("[阶段B] 放弃：无人接收")
		}
	}()
	time.Sleep(2 * abandonAfter) // 故意不接收 orphan，观察超时分支
	fmt.Println("[阶段B] 主 goroutine 正常收尾，阻塞的发送没有拖垮程序")
}

11 · 内存去哪了

一句话模型：变量分配在栈还是堆由编译器逃逸分析决定，GC 只回收不可达对象，但"可达"可能来自你没意识到的引用。

先看一个现象

一个函数把局部变量的地址返回出去：

go
func newValue() *int {
	x := 42
	return &x
}

p := newValue()
fmt.Println(*p) // 42

你以为 x 是局部变量，函数一返回栈帧就被回收，这个指针指向的是一块失效内存。实际 *p 稳稳读到 42，而且每次调用拿到的都是独立对象——x 的作用域结束了，但它指向的那块存储被延长了寿命。

再看一个几乎一样的写法：

go
func useLocal() int {
	x := 42
	p := &x
	return *p
}

这里同样取了 &，x 却可能根本没进堆，甚至被编译器折叠成常量 42。同样是"局部变量取地址"，一个逃逸、一个不逃逸。决定因素不是那个 &，而是这份数据还要活多久。

再抛一个更隐蔽的：

go
func counter() func() int {
	count := 0
	return func() int { count++; return count }
}

next := counter()
fmt.Println(next(), next()) // 1 2

你以为外层函数一返回，count 就随栈帧一起消失；实际两次调用读到 1 和 2——闭包把 count 连同它的存储一起带走了。这三段代码构成了本篇的三个问题：地址能返回、地址可能不逃逸、闭包能延长寿命。

先建立直觉

把图记住一句：编译器管前半段，GC 管后半段，两者用的是不同标准。 源代码里你看不到"堆"这个关键字，它是编译器替你做的决定。

机制拆成四步

1. 作用域问"名字在哪可见"，生命周期问"数据要活多久"

x 的作用域仅限 newValue 函数体，出了花括号这个名字就不存在了。但 return &x 把它的地址交给了调用者，调用者可能在函数返回很久之后才解引用。语言必须保证这个操作安全，于是编译器让 x 的存储活得比它的名字更久。

这就是栈与堆的真正分界线：栈帧随函数调用压入、随返回弹出，适合"活不过本次调用"的数据；堆由运行时分配器管理，适合"寿命超出当前调用"的数据。它们不是源码上的标签，而是对生命周期需求的回应。

2. 逃逸分析是编译期的寿命推断，不是语法规则

编译器在编译期追踪每个值"会不会被当前调用之外的东西引用"。返回地址、存进接口、被闭包捕获、赋值给全局或堆上的结构，都会把寿命传递给函数之外。

为什么 &x 不一定是逃逸？因为编译器会顺着指针继续看：在 useLocal 里，p 只用于一次 *p，没有任何副本离开函数，编译器能证明这份数据在栈帧存活期内就能算完，于是把它留在栈上。取地址只是分析线索，不是结论。

让编译器把理由说出来：

bash
go build -gcflags='-m' .

日志里的 moved to heap: x、&x escapes to heap 就是这次编译的判断。注意它是"这次编译的结果"，不是语言规范承诺；内联策略或编译器版本变了，输出也可能变。Demo 里的 //go:noinline 只是禁止内联方便观察，并不强制堆分配。

3. GC 从 roots 判定可达，不看变量声明位置

分配只是故事的一半。对象什么时候能回收？GC 以 roots 为起点，沿指针遍历所有能到达的对象并标记，剩下的就是垃圾。它不关心对象最初是在栈上还是堆上声明的，只关心"现在还有没有路能走到它"。

为什么这点重要？因为你以为没人用的对象，可能仍被一条你没注意到的引用拴着。闭包捕获的变量、接口里装箱的值、全局切片里残留的元素，都是常见的"隐藏的根"。调用 runtime.GC() 不会让它们消失——GC 只看可达性。

注意下面这段代码里没有出现一个 &：

go
var saved []any

func keepAlive(v int) {
	saved = append(saved, v) // v 装箱进接口，又被全局切片持有
}

v 仍然必须活过 keepAlive，因为它被装进接口值、又存进了包级变量。判断逃逸时若只盯着取地址符，就会漏掉这类情况。沿着"这个值被谁保存"这条线走，比数 & 可靠得多。

4. 闭包捕获的是"环境"，不是函数体

counter() 返回的匿名函数引用了外层变量 count。外层函数早已返回，但函数值被调用者持有，它需要一个地方继续存放 count，于是 count 被搬到堆，随闭包环境一起存活：

go
func counter() func() int {
	count := 0
	return func() int { count++; return count }
}

每次调用 next() 读到的是连续递增的同一个 count，不是重新创建的副本。这里逃逸的不是"函数体"，而是被环境引用的那份变量存储。如果闭包只在函数内部短暂使用，编译器完全可能做出不同的决定。

动手验证看分配趋势与 GC 前后的内存变化

先预测：构造 2000 个逃逸对象后，累计分配次数 Mallocs 会怎么变？

运行：cd examples/minimal/11-memory-escape && go run .（标有「可调参数」的常量就是旋钮）

go
package main

import (
	"fmt"
	"runtime"
)

// 可调参数：构造多少个逃逸到堆的大对象
const escapedObjects = 2000

// 可调参数：闭包计数器递增几次
const closureSteps = 3

// block 故意做大一点，让 GC 前后的 HeapAlloc 差异盖过噪声。
type block struct {
	data [64]byte
}

// newValue 返回局部变量的地址：x 必须活过本函数，编译器把它挪到堆。
func newValue() *int {
	x := 42
	return &x
}

// newBlock 同样返回堆对象的指针，用来观察分配与回收。
func newBlock() *block {
	b := block{}
	b.data[0] = 1
	return &b
}

// counter 返回一个闭包：count 被闭包环境捕获，函数返回后仍须存活。
func counter() func() int {
	count := 0
	return func() int {
		count++
		return count
	}
}

func stats() (uint64, uint64) {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return m.Mallocs, m.HeapAlloc
}

func main() {
	// 现象一：局部变量地址被返回后，数据仍然有效。
	p := newValue()
	fmt.Printf("返回局部变量指针：*p=%d\n", *p)

	// 现象二：闭包捕获的变量在外层函数返回后继续存活。
	next := counter()
	for i := 1; i <= closureSteps; i++ {
		fmt.Printf("闭包第 %d 次调用 = %d\n", i, next())
	}

	// 验证一：构造一批逃逸对象，累计分配次数只增不减。
	beforeMallocs, _ := stats()
	keep := make([]*block, 0, escapedObjects)
	for i := 0; i < escapedObjects; i++ {
		keep = append(keep, newBlock())
	}
	afterMallocs, _ := stats()
	fmt.Printf("构造 %d 个逃逸对象：Mallocs 增加 = %t\n", escapedObjects, afterMallocs > beforeMallocs)
	fmt.Printf("  累计分配次数：%d -> %d\n", beforeMallocs, afterMallocs)

	// 验证二：断开引用后这些对象不可达，GC 才可能回收它们。
	_, heapBeforeGC := stats()
	keep = nil
	runtime.GC()
	_, heapAfterGC := stats()
	fmt.Printf("断开引用并 GC：HeapAlloc 下降 = %t\n", heapAfterGC < heapBeforeGC)
	fmt.Printf("  HeapAlloc：%d -> %d（趋势，非精确字节）\n", heapBeforeGC, heapAfterGC)

	// 仍被变量引用的对象，GC 动不了它。
	live := newValue()
	runtime.GC()
	fmt.Printf("GC 后仍可达的 live：*live=%d\n", *live)
}

12 · IO 是组合出来的

一句话模型：io.Reader/Writer 是两个极小接口，能力靠包装层叠加；组合改变"经过时发生什么"，不改变字节本身；谁打开谁负责 Close。

先看一个现象

把一段字符串复制进缓冲区，顺便想知道"经过了多少字节"：

go
var dst bytes.Buffer
written, _ := io.Copy(&dst, strings.NewReader(data))

你以为要统计字节数就得改复制循环，或者到处插打印。实际在数据源外面套一层自定义 Reader，io.Copy 毫无感知，账已经记完了：

go
type countingReader struct {
    src   io.Reader
    total int
}

func (c *countingReader) Read(p []byte) (int, error) {
    n, err := c.src.Read(p)
    c.total += n
    return n, err
}

written, _ := io.Copy(&dst, &countingReader{src: strings.NewReader(data)})

你以为包装会动数据。实际字节一个不少：计数层只是站在 Read 的必经之路上记一笔，io.Copy 只认 Read(p []byte) (n int, err error) 这个签名，根本不知道自己读的是 strings.Reader 还是七层包装。再加一层 io.TeeReader，一份数据还能同时抄送给第二个出口——能力就是这样一层层叠上去的。

先建立直觉

图上最该带走的一句话：每一层只做一件事，责任却不随字节一起往下传。 包装可以无限叠加，Close 不会跟着叠——它始终停在打开资源的那一行。

所以读一段 IO 代码的正确姿势，是先把它拆成"哪些层在搬运字节、哪些层在观察字节、谁负责关闭"，而不是逐个记 API。下面按这个顺序拆机制。

机制拆成四步

1. 接口为什么这么小

io.Reader 与 io.Writer 各只有一个方法。为什么故意这么小？约束越少，能接入的东西越多：文件、网络连接、字符串、内存块、压缩流，只要能实现"把字节填进 p 并报告数量"就能当 Reader 用。同理，任何中间件只要也实现这个签名，就能插进任意两段 IO 代码之间，双方都不用改一行。

这就是组合的入口：io.Copy(dst, src) 不关心 src 是什么，于是"计数""限量""分流"全部可以做成外面包一层的 Reader，而不是给 Copy 加参数。

2. 每层包装只做一件事

标准库的包装层各自只负责一件事：bufio.Reader 攒批，减少底层调用次数；io.TeeReader 分流，读一路、抄送一路；io.MultiReader 拼接，把多个源粘成一个源；io.LimitReader 限量，到上限就报告 EOF。

组合的顺序决定行为：计数层包在最外层，看到的是 io.Copy 每次索要的量（默认 32KB 大缓冲）；包在 bufio 里面，看到的是攒批之后取底层的大块。数据一样，经过方式不一样——排链的时候要按"谁观察谁的节奏"决定谁包谁。

一条链写出来就是把源从里往外一层层包住：

go
src := strings.NewReader(data)        // 源
counted := &countingReader{src: src}  // 第一层：记账
tee := io.TeeReader(counted, side)    // 第二层：分流
io.Copy(&dst, tee)                    // 汇聚：字节最终到这里

为什么 io.TeeReader 的副本是"边读边抄"而不是事后复制？它没有地方存放整份数据——它在每次 Read 成功后，立刻把刚读到的 p[:n] 写给分流目标。这决定了它的适用边界：适合"流过什么就留一份什么"，不适合"回头再看一遍"的随机访问需求。

3. io.Copy 的循环：读到 EOF 为止

io.Copy 的全部工作是"读一块、写一块，直到 EOF 或出错"。为什么它不要求一次读满？因为 Read 的契约允许短读：n 可以小于 len(p)，甚至 n > 0 和 err == io.EOF 同一次调用一起返回。手工写一遍这个循环，契约就摆在明面上：

go
buf := make([]byte, 32*1024)
for {
    n, err := src.Read(buf)
    if n > 0 {
        dst.Write(buf[:n]) // 先处理读到的，短读不是错误
    }
    if err == io.EOF {
        break // EOF 是正常结束，不是失败
    }
}

这个契约正是计数 Demo 能工作的原因：计数层每次只交 4 个字节，io.Copy 不抱怨、不假设，照常一轮轮循环，最终 written 与累计字节分毫不差。

4. Close 的责任：谁打开谁负责

包装层叠加能力，但不接管生命周期：io.TeeReader、io.LimitReader、io.MultiReader 都不会替你关闭底层 Reader。为什么？它们只是"借用"——如果包装层擅自 Close，一个只读前几个字节的临时包装就会把还要用的资源关掉。

规则因此很朴素：谁打开，谁负责 Close；要转移所有权，就显式交接——签名收 io.ReadCloser 并说明"会关闭"，或反过来明确"借用、不关闭"。defer 写在打开的那一行旁边，panic 路径也覆盖得到。

你想要的组合方式
统计经过的字节自定义计数 Reader 包住源
一份数据两处用io.TeeReader
两个源当一个用io.MultiReader
最多读 N 字节io.LimitReader

动手验证计数、分流与一条被记着的 Close

先预测：计数层每次 Read 最多交 readChunk 字节，最终计数还会等于 io.Copy 的 written 吗？

运行：cd examples/minimal/12-io-boundary && go run .（标有「可调参数」的常量就是旋钮）

go
package main

import (
	"bytes"
	"fmt"
	"io"
	"strings"
)

const readChunk = 4 // 可调参数：计数层每次最多交出的字节数，改成 8 只改变节奏，不改变总量

// countingReader 在 Read 路径上插一个观察点：字节原样通过，只是记一笔账。
type countingReader struct {
	src   io.Reader
	total int // 累计经过的字节数
	calls int // 累计被调用的次数
}

func (c *countingReader) Read(p []byte) (int, error) {
	if len(p) > readChunk {
		p = p[:readChunk] // 主动短读：合法行为，调用方必须能处理
	}
	n, err := c.src.Read(p)
	c.total += n
	c.calls++
	return n, err
}

// tracingCloser 演示 Close 责任：谁打开，谁负责关闭。
type tracingCloser struct {
	io.Reader
	name string
}

func (t *tracingCloser) Close() error {
	fmt.Printf("[关闭] %s：已关闭\n", t.name)
	return nil
}

func main() {
	fmt.Println("[管道] 源 → 计数 → 分流(Tee) → 汇聚(bytes.Buffer)")

	counter := &countingReader{src: strings.NewReader("hello, 组合出来的 io")}
	side := &bytes.Buffer{}
	tee := io.TeeReader(counter, side) // 分流：流入主路的同时抄送一份副本

	var dst bytes.Buffer
	written, err := io.Copy(&dst, tee)
	fmt.Printf("[复制] written=%d err=%v\n", written, err)
	fmt.Printf("[计数] 经 %d 次 Read，累计 %d 字节，与 written 一致：%v\n",
		counter.calls, counter.total, counter.total == int(written))
	fmt.Printf("[内容] 主路 dst=%q 副本 side=%q\n", dst.String(), side.String())

	fmt.Println("[关闭] Close 的责任：谁打开谁负责")
	src := &tracingCloser{Reader: strings.NewReader("借用中的数据"), name: "source"}
	defer src.Close() // 打开者负责关闭；包装层与 io.Copy 都不会替你调
	n, _ := io.Copy(io.Discard, src)
	fmt.Printf("[关闭] 借用期间读走 %d 字节，关闭仍归打开者\n", n)
}

13 · JSON 是另一套边界

一句话模型：结构体是你程序的类型世界，JSON 是外部文本世界；struct tag 是两套世界之间的翻译规则，而翻译永远有损——未导出字段、未知字段、时间与数字都各有边界。

先看一个现象

同一个 user 值，编码再解码，回不到原样：

go
type user struct {
	ID   int64  `json:"id"`
	Name string `json:"name"`
	Note string `json:"note,omitempty"`
	kind string // 内部分类，不该离开进程
}

u := user{ID: 7, Name: "ada", kind: "internal"}
b, _ := json.Marshal(u)
fmt.Println(string(b)) // {"id":7,"name":"ada"}

var back user
_ = json.Unmarshal(b, &back)
fmt.Println(back.kind) // 空串：internal 留在了门内

你以为 Marshal/Unmarshal 是"原样搬出去、原样搬回来"，实际 kind 根本没出门。

反方向同样有筛子。对方发来一个结构体里没有的字段：

go
input := []byte(`{"id":7,"name":"ada","role":"admin"}`)

var lenient user
_ = json.Unmarshal(input, &lenient) // err = nil
fmt.Println(lenient)                // {7 ada  }，role 被静默丢弃

你以为多出来的字段至少会给个警告，实际什么都没有——哪怕它其实是 nmae 这样拼错的 name，也照样被当成未知字段吞掉，业务拿到一串零值还以为成功了。

还有第三处：缺失字段也不报错。{"id":7} 可以成功解码，Name 只是零值。翻译不是校验，语法通过不代表信息完整。

两次翻译，两次有损。判断数据穿过边界后会变成什么，靠的不是"字段有没有写 tag"，而是知道翻译规则在哪一侧生效、丢弃发生在哪一步。

先建立直觉

图要读出一件事：翻译规则只覆盖两侧都"登记过"的字段。 没登记的——未导出、主动排除、对方多发的——各有各的下场，而且大多是静默的。

四种门禁规则放在一起对照，它们分属三个不同的来源：

规则来源编码侧行为解码侧行为
字段未导出Go 语言规则不出门不写入
json:"-"开发者决定主动排除主动排除
omitemptytag 选项零值时整键省略无作用
默认规则（无开关）库的兼容性决策——未知字段静默丢弃

机制拆成四步

1. 翻译规则写在 tag 里，但只有导出字段有资格参加

encoding/json 在你的包之外工作，而 Go 的可见性规则禁止包外代码读写未导出字段。所以未导出字段进不了翻译——这不是库的疏忽，是语言边界挡在那里。

tag 的另一个作用是改名：JSON 侧习惯小写或下划线命名，ID 映射成 id 由 tag 完成，不必让 Go 的导出命名向协议妥协。不写 tag 时默认用字段原名，ID 会变成 ID。

json:"-" 则是你主动把一个可导出的字段划出边界："这个字段允许包内其他代码看，但不许翻译出去。"三者性质不同：语言规则动不了，命名约定可以商量，开发者的排除写一行就能改。

2. omitempty 在编码侧省略零值：缺席与零值被合并

omitempty 让空串、0、nil、false 这类零值不出门。为什么说它有损？因为缺席只有一种形态，缺席的原因却有两种——"发送方没填"和"发送方填了零值"。

go
a := user{ID: 7, Name: "ada"}                    // 没填 Note
b := user{ID: 7, Name: "ada", Note: ""}          // 明确填了空串
// Marshal(a) == Marshal(b)："note" 都不出现在文本里

解码侧只能观察到"键缺席"，后者的信息在编码那一步就被合并掉了。往返之后你手里只有零值，永远不知道它是不是被主动省略的。真要区分，得换成 *string 这类能表达"存在但为空"的表示，而不是指望 tag。

3. 解码默认忽略未知字段：这是兼容性决策，不是疏忽

为什么默认不报错？因为协议要演进：服务端新增一个字段，不能让所有旧客户端当场报错。忽略未知字段是向前兼容的代价。

代价的另一面是拼写错误（nmae）也被当未知字段吞掉。要拦住它，用 Decoder 收紧规则：

go
dec := json.NewDecoder(bytes.NewReader(input))
dec.DisallowUnknownFields()
err := dec.Decode(&u) // json: unknown field "nmae"

这是用向前兼容换拼写检查：规则收紧后，服务端再加新字段，你的旧程序也会报错。所以它适合协议收口处——配置加载、内部服务之间的固定约定——而不是所有对外接口一刀切。它作用于标准解码路径上的每一层嵌套结构体，但自定义了 UnmarshalJSON 的类型会绕开默认字段处理，要靠嵌套类型的测试确认。

4. 时间与数字：类型信息不会跟着值过境

JSON 里没有时间类型。time.Time 能进 JSON，是因为它实现了 MarshalJSON，把自己翻译成 RFC 3339 格式的字符串，解码时再按同一格式解析回来：

go
t := time.Date(2026, 11, 25, 7, 15, 55, 123000000, time.UTC)

b, _ := json.Marshal(t)
fmt.Println(string(b)) // "2026-11-25T07:15:55.123Z"

fmt.Println(t.String()) // 2026-11-25 07:15:55.123 +0000 UTC

往返后 Equal 成立，但两边文本是两套表示：Go 的 String() 和 JSON 的 RFC 3339 是两种书写习惯，编码时选哪套由类型的 MarshalJSON 决定，不由你每次调用决定。

数字同理。JSON 只规定"数字"这一种语法，不带 Go 类型：int64 的精确只保证到你这一侧。同一个 9007199254740993，Go 编码出去原样无误，接收方若把它解析成双精度浮点，末位就可能变成 9007199254740992。类型信息不随值过境，所以跨系统协议必须连"接收方用什么类型"一起约定，不能只约定字段名。

14 · 组合、嵌入与包边界

一句话模型：Go 的复用靠小接口 + 组合，嵌入是委托语法而不是继承；包边界靠导出与否表达。

先看一个现象

日志是个到处都要用的能力。先定义一个只写一条日志的接口：

go
type Logger interface {
	Log(msg string)
}

你以为要支持"带前缀的日志"，就得新建一个日志类型、把写日志的细节再抄一遍。实际可以用一个结构体把已有的 Logger 包起来：

go
type prefixLogger struct {
	Logger
	prefix string
}

func (p prefixLogger) Log(msg string) {
	p.Logger.Log(p.prefix + msg)
}

prefixLogger 没有实现任何"写日志"的细节，它只在消息前面拼了个前缀，然后把活交给里面那个 Logger。更反直觉的是那个没有字段名的 Logger：它叫嵌入字段，看起来很像继承，但 prefixLogger 并不是"一种" Logger，它只是"拥有"一个 Logger，并在自己这一层决定何时调用它。

这套写法能一路叠下去：[app] 包一层，[trace] 再包一层，每层只关心自己加的那点东西。而调用方从头到尾只认那个只有一行方法的小接口。

先建立直觉

图里最该记住的是"拥有"和"是一种"的差别：组合表达的是我拿了一个部件来用，继承表达的是我本身就是那个东西。Go 只提供前者。

机制拆成四步

1. 小接口描述能力，而且由使用方定义

Logger 只有 Log(msg string) 一个方法。为什么接口要小？因为接口越大，实现它要背的东西越多，能实现的类型就越少。小接口只问一句"你能不能干这件事"，让更多类型天然满足它。

更关键的是：接口定义在使用方，不在实现方。 写日志装饰器的人需要"能写一条消息"这个能力，于是就地定义 Logger；consoleLogger 只是恰好有 Log 方法，它不需要知道自己被某个接口点名了。这就是 Go 的隐式满足——没有 implements 关键字，方法集对得上就成立。

一个类型可以同时满足很多个小接口，因为它的方法集里各取了一部分——这也是小接口容易复用的原因。

2. 组合是"拥有部件并决定何时调用"

显式组合是老老实实写一个命名字段：

go
type Service struct {
	log Logger // 命名字段：只暴露你显式转发的能力
}

func (s Service) Load(id string) {
	s.log.Log("loading " + id)
}

为什么有时更偏爱命名字段而不是嵌入？因为嵌入会把内层类型的所有方法提升到外层。假设内层的类型有 20 个方法，你只想复用其中 1 个，嵌入会让调用方看到 20 个方法——这叫能力泄漏。命名字段加一个转发方法，则精确控制对外只露出那 1 个。

组合的核心动作是"决定何时调用"：组件不会自己跑起来，外层在合适的时机调用它，因此依赖关系是显式的、可读的。换句话说，组合把"谁依赖谁"写在代码里，而不是藏在类型层级里。

3. 嵌入是委托语法，方法提升不是继承

嵌入字段的写法是只写类型、不写字段名：

go
type prefixLogger struct {
	Logger // 字段名就是 Logger，类型也是 Logger
	prefix string
}

编译器做两件事：把 Logger 的字段和方法提升到 prefixLogger，让 p.Log(...) 可以直接写；同时生成一个字段 p.Logger 让你能显式访问被包住的实例。为什么还说它不是继承？因为提升只是名称查找规则——查不到才去内层找，不复制任何数据，也不建立"是一个"的类型关系。

既然 prefixLogger 自己定义了 Log，外层这个就会遮蔽提升来的那个。想同时调用两者，只能像 demo 那样显式写 p.Logger.Log(...)；Go 不会自动帮你把两个同名方法串起来。

还有两条边界要留意：嵌入 *T 时，外层和内层共享同一个对象，改内层就是改外层看到的那份；嵌入 nil 指针则在访问提升字段时直接 panic，需要构造器保证初始化。

4. 包边界用大小写表达公开承诺

复用不止发生在类型之间，也发生在包之间。Go 用标识符首字母的大小写划了一条硬边界：

go
// 包 logging
type Logger interface{ Log(string) }   // 导出：包外可用
type consoleLogger struct{}            // 未导出：包外不可见
func New() Logger { return consoleLogger{} } // 导出构造函数

为什么要让构造函数返回接口而不是具体类型？因为具体类型 consoleLogger 是未导出的，包外代码拿不到它，只能按住 Logger 接口使用。于是实现细节（比如换成一个写文件的 logger）可以在包内改写，而所有调用方毫发无伤。

大小写不是风格建议，是编译器强制的规则：未导出的标识符跨包不可见。它和嵌入的字段提升一起，构成了 Go 的两层封装——包边界控制"谁能看见"，组合结构控制"谁能调用"。

const outerPrefix = "[app] "

}

	name string
}

}

type prefixLogger struct {

	prefix string
	name   string
}

func (p prefixLogger) Log(msg string) {

	p.Logger.Log(p.prefix + msg) // 显式委托给被嵌入的 Logger
}

func main() {
	base := consoleLogger{name: "console"}
	inner := prefixLogger{Logger: base, prefix: "[inner] ", name: "prefix-1"}
	outer := prefixLogger{Logger: inner, prefix: outerPrefix, name: "prefix-2"}

	// 调用方只认 Logger 小接口，看不到具体实现类型。
	var l Logger = outer
	for i := 1; i <= repeat; i++ {
		fmt.Printf("第 %d 条消息：\n", i)
		l.Log(fmt.Sprintf("hello-%d", i))
	}
	fmt.Println("委托链：prefix-2 → prefix-1 → console")
}

15 · 一次请求穿过哪些边界

一句话模型：Server 管连接与超时，Mux 管路由，Handler 管一次请求；谁拥有资源谁负责关闭。

先看一个现象

客户端发来 DELETE /tasks/42，服务端确实注册了 /tasks/{id}，你以为会返回 200 或者"找不到"的 404，实际拿到的是 405 Method Not Allowed。换个请求 GET /unknown/404，同样是"没有这个资源"，这次却返回 404。

go
mux.HandleFunc("GET /tasks/{id}", getTask)
mux.HandleFunc("POST /tasks", createTask)

两个请求都没被业务代码碰到，响应却不同。这说明在 Handler 之前已经有一层做了判断，而且它看的不只是路径，还有方法。再看一个更隐蔽的故障：Handler 里启动了一个后台任务就返回，连接被回收了，那个任务还在跑——谁该为它负责？

一次请求要穿过好几道边界，每道边界只回答自己的问题。把责任放错层，就会出现"路径对了却 405""超时设了却仍卡死"这类看着像业务的传输问题。最小对照是这样的：

text
GET    /healthz       -> 200
DELETE /tasks/42      -> 405   路径命中，方法不允许
GET    /unknown/404   -> 404   没有任何模式命中

三个请求都没碰到业务代码，状态码却已经分出高下——判断发生在 Handler 之前。

先建立直觉

图要读出一条原则：每一层只做自己那一格的事。 Server 不认识你的任务，Mux 不查询数据库，Handler 不去监听端口。分层不是为了目录好看，而是为了让某一层的问题能被单独观察和替换。

机制拆成四步

1. Server 管连接与超时：它服务很多请求，不认识你的业务

http.Server 负责监听、接受连接、解析 HTTP、在请求结束后回收或复用连接。一个 Server 服务大量请求，因此它的配置都是连接级的，不是业务级的：

go
server := &http.Server{
	Addr:              "127.0.0.1:8080",
	Handler:           newHandler(),
	ReadHeaderTimeout: 5 * time.Second,
	IdleTimeout:       60 * time.Second,
}

为什么要单独设 ReadHeaderTimeout？因为"连上但不发完整请求头"是一种廉价攻击：客户端几乎不花成本，服务端却要为它占着一个连接和一个 Goroutine。读超时要分两段，是因为"慢请求头"和"慢请求体"是两种不同的故障，一刀切会误伤正常的大文件上传。

四类超时各封一种故障，别指望一个数字全包：

配置封住什么封不住什么
ReadHeaderTimeout连上后迟迟不发完整请求头请求体传输慢
ReadTimeout请求体读取得太慢Handler 内部执行太久
WriteTimeout响应写不出去或客户端不接收数据库查询卡住
IdleTimeoutKeep-Alive 连接长期空占活跃请求的处理时限

2. Mux 管路由：方法也是路由的一部分

Go 1.22 起，模式可以把方法写进去：

go
mux.HandleFunc("GET /tasks/{id}", getTask)
mux.HandleFunc("POST /tasks", createTask)

GET /tasks/42 命中第一个，POST /tasks 命中第二个。那 DELETE /tasks/42 呢？路径 /tasks/{id} 是命中的，但方法对不上，Mux 返回 405，并通过 Allow 头告知允许的方法；GET /unknown/404 则没有任何模式匹配，返回 404。

为什么要把方法放进路由，而不是在 Handler 里 if r.Method != "GET"？因为让 Mux 更早拒绝不匹配请求，Handler 就能只处理自己该处理的事；同时 404 与 405 的语义也自动正确了——路径存在而方法不对，本就该是 405。

路径变量 {id} 只匹配一个路径段，{rest...} 才匹配多级。取出来的 r.PathValue("id") 是客户端输入，不是可信标识；路由匹配不能替代认证与授权。

3. Handler 管一次请求：不要把请求状态放进字段

Handler 的接口只有一个方法：

go
type Handler interface {
	ServeHTTP(w ResponseWriter, r *Request)
}

它只表达"收到请求、写响应"，不表达监听和连接回收。为什么这点关键？因为同一个 Handler 实例会被并发调用。把标题、用户身份、临时结果存成 Handler 的字段，就会在多个请求之间串扰，还产生数据竞争。请求数据应放在局部变量或 r.Context() 里：

go
func bad(w http.ResponseWriter, r *http.Request) {
	h.user = r.Header.Get("User") // 错：并发请求互相覆盖
}

func good(w http.ResponseWriter, r *http.Request) {
	user := r.Header.Get("User") // 对：每次请求一份局部变量
}

这也解释了为什么 Handler 可以单独测试：用 httptest.NewRequest 造请求、httptest.NewRecorder 接响应，直接调 ServeHTTP，不需要监听端口、不需要网络。demo 正是这么做的。

4. 谁拥有资源谁关闭：超时封不住业务

标准 net/http Server 通常会在 Handler 返回后关闭请求体，但 demo 仍显式写 defer r.Body.Close()。为什么？因为显式释放让责任在代码里可见；当你替换 Server、包装 Body 或换用测试替身时，这份可见性就是安全网。

WriteTimeout 尤其容易被误解。它限制的是"写响应"这一步，不会在数据库查询卡住时主动取消查询。要让业务也能退出，必须把 r.Context() 的取消信号传到下游——数据库调用、出站 HTTP 请求都要真正监听它。Handler 若启动了后台 Goroutine，还得自己负责停机和等待；Handler 返回不代表后台任务结束。

	"io"
	"net/http"
	"net/http/httptest"
	"strings"

type trackedBody struct {
	io.Reader
	closed bool
}

func (b *trackedBody) Close() error {
	b.closed = true
	return nil
}

func health(w http.ResponseWriter, r *http.Request) {
	w.WriteHeader(http.StatusOK)
}

func getTask(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintf(w, "task id=%s", r.PathValue("id"))
}

func createTask(w http.ResponseWriter, r *http.Request) {
	defer r.Body.Close() // 谁持有 Body，谁负责关掉它
	_, _ = io.ReadAll(r.Body)
	w.WriteHeader(http.StatusCreated)
}

func newHandler() http.Handler {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /healthz", health)
	mux.HandleFunc("GET /tasks/{id}", getTask)
	mux.HandleFunc("POST /tasks", createTask)
	return mux
}

func statusOf(h http.Handler, method, target string) int {
	req := httptest.NewRequest(method, target, nil)
	rec := httptest.NewRecorder()
	h.ServeHTTP(rec, req)
	return rec.Code
}

func main() {

		{"GET", "/tasks/" + taskID},

		{"GET", "/unknown/" + unknownID},

16 · 事务的边界

一句话模型：事务把"多步写要么全成功要么全撤销"变成一个边界；出错路径必须显式 Rollback，成功路径必须显式 Commit；拼接 SQL 字符串把数据变成代码，参数化查询把数据留在数据侧。

先看一个现象

转账程序做两步写：从 alice 扣 300，给 carol 加 300。每条语句都单独执行：

go
db.Exec("UPDATE accounts SET balance = balance - 300 WHERE name = 'alice'")
db.Exec("UPDATE accounts SET balance = balance + 300 WHERE name = 'carol'")
// 第二句失败：alice 的 300 元去了哪里？

你以为"每条语句执行成功就没事"，实际两条语句各自生效，第二步失败时第一步已经收不回来——钱扣了，对方没收到。半成功比彻底失败更难处理：它不会被重试修复，盲目重试还会把第一步再扣一次。

再看另一类事故。用户名是 ' OR '1'='1，程序把它拼进查询条件：

text
SELECT * FROM users WHERE name = '' OR '1'='1'

输入里的引号闭合了字符串，OR '1'='1' 恒为真，条件匹配了全部行。攻击者没有改代码，只是把数据变成了语法——拼进 SQL 的每个字符都获得了改变语法的资格。

这两类问题的答案指向同一个方向：给写入划一条要么全成、要么全撤的边界；给查询划一条数据永远只是数据的边界。

先建立直觉

图要读出一条原则：边界由两个显式动作闭合——Commit 或 Rollback，没有第三个结局。 草稿区里的修改在边界闭合之前，对外既不生效也不算失败。

两条结束路径对照着记：

结束动作触发条件对外效果之后再调用它
Commit所有语句都成功草稿一次性生效得到"事务已结束"，数据不撤
Rollback任一步失败（或提前返回）草稿整体丢弃同样得到"事务已结束"

机制拆成四步

1. Begin 划定边界：语句先落在草稿区

Begin 之后的所有修改都挂在事务上，而不是立刻生效。为什么要有草稿区？一方面，别的会话在 Commit 之前看不到这些中间状态，不会读到"扣了款还没入账"的半成品；另一方面，也是对你更重要的——它给你一个可以整体撤销的单位。

没有草稿区会怎样？撤销就得靠反向补偿：给 alice 再加一次 300。而补偿本身又可能失败，失败后还要再补偿补偿，错误滚雪球。数据库把这个问题收进了边界里：要么草稿全部生效，要么全部当没发生，补偿逻辑不用你写。

2. 出错路径必须显式 Rollback：defer 惯用法

事务的惯用写法是 Begin 之后立刻 defer tx.Rollback()：

go
tx, err := db.BeginTx(ctx, nil)
if err != nil {
	return err
}
defer tx.Rollback() // 只承担失败路径的清理责任

if err := debit(ctx, tx, fromID, amount); err != nil {
	return err // defer 触发，草稿丢弃
}
if err := credit(ctx, tx, toID, amount); err != nil {
	return err // 第一步的扣款一并撤销
}
return tx.Commit()

为什么用 defer？因为事务里任何一步都可能 return——错误检查、余额不足、Context 取消——手工在每条路径上补 Rollback 必有遗漏。defer 把清理责任收敛到一个位置，新增失败分支时不用惦记它。

Commit 之后延迟执行的 Rollback 不会撤销已提交的数据，它只会得到"事务已结束"。所以这一行不会误伤成功路径，它存在的意义只有一个：保证失败路径永远有一条退路。

3. 成功路径必须显式 Commit：边界要闭合

草稿区的修改只有 Commit 才对外生效。为什么不省掉它、让函数返回时自动提交？因为"自动"意味着边界不再由你控制：函数里多加一段计算、多等一次外部调用，提交时机就跟着漂移，事务持有锁和连接的时间也随之失控。

显式 Commit 让"哪些写属于同一个工作单元"在代码里可见：从 Begin 到 Commit 之间的语句，就是你向数据库声明的一个不可分割单元。反过来的教训同样成立：

go
tx, _ := db.BeginTx(ctx, nil)
tx.Exec(...) // 写进草稿
return err   // 提前返回，没有 Commit：草稿被丢弃，数据消失且无报错

Begin 之后忘了 Commit，连接归还时草稿被丢弃，写入悄无声息地消失。边界没有闭合，前面的步骤就都白做。

4. 拼接与参数化：数据与代码之间隔着一条通道

SQL 由两部分组成：结构（查哪张表、按什么条件、按什么排序）由开发者写死；值（用户名、ID、金额）运行时才确定。拼接字符串把两者揉进同一段文本，输入里的引号就有了改变语法的资格。参数化查询把通道分开：

go
// 拼接：输入进入 SQL 文本，被当语法解析
query := fmt.Sprintf("SELECT * FROM users WHERE name = '%s'", input)

// 参数化：文本固定，输入走参数通道
row := db.QueryRowContext(ctx, "SELECT * FROM users WHERE name = $1", input)

参数化不是"帮你转义危险字符"——转义是字符串层面的补丁，规则随字符集和上下文变化，手工维护必漏。它是通道分离：SQL 文本先定死，输入从头到尾只是与字段做相等比较的一个值，无论内容是什么。

有一个例外要记住：ORDER BY 后的列名、动态表名这类标识符不能当值绑定。把它们当参数，数据库会把它读成一个常量表达式而不是列；直接拼接又回到注入风险。正确做法是白名单映射——外部输入只用来"选择"开发者写死的选项，永远不直接进入 SQL 文本。

动手验证

动手验证内存版 miniTx：Commit、Rollback 与两种查询构造

先预测：第二步入账失败后，alice 的余额是多少，第一步的扣款去了哪里？

运行：cd examples/minimal/16-database-transaction && go run .（标有「可调参数」的常量就是旋钮）

go
package main

import (
	"fmt"
	"strings"
)

// 可调参数：转账金额
const amount = 300

// 可调参数：查询输入；这个值会把拼接版 SQL 变成另一种语法
const userInput = "' OR '1'='1"

// account 与 store 模拟一张两列的表。
type account struct {
	name    string
	balance int
}

type store struct {
	rows map[string]*account
}

func newStore(initial map[string]int) *store {
	s := &store{rows: map[string]*account{}}
	for name, bal := range initial {
		s.rows[name] = &account{name: name, balance: bal}
	}
	return s
}

// miniTx 是内存版事务：exec 只写草稿区，commit 一次性生效，rollback 整体丢弃。
// 真实项目请用 database/sql + 驱动的事务，边界语义与此一致，草稿区由数据库管理。
type miniTx struct {
	s      *store
	staged map[string]int // 草稿区：名字 → 提交后的余额
	failed error          // 第一步失败后，后续语句不再执行
}

func (s *store) begin() *miniTx {
	return &miniTx{s: s, staged: map[string]int{}}
}

func (tx *miniTx) exec(name string, delta int) error {
	if tx.failed != nil {
		return tx.failed
	}
	row, ok := tx.s.rows[name]
	if !ok {
		tx.failed = fmt.Errorf("account %q not found", name)
		return tx.failed
	}
	tx.staged[name] = row.balance + delta
	return nil
}

func (tx *miniTx) commit() error {
	if tx.failed != nil {
		return tx.failed
	}
	for name, bal := range tx.staged {
		tx.s.rows[name].balance = bal
	}
	return nil
}

func (tx *miniTx) rollback() {
	tx.staged = nil // 草稿整体丢弃，第一步的修改一并撤销
}

// transfer 是典型的两步写：任何一步失败，整体都必须当作没发生。
func transfer(s *store, from, to string, amt int) error {
	tx := s.begin()
	defer tx.rollback() // 惯用法：只承担失败路径的清理；commit 之后它什么也不做
	if err := tx.exec(from, -amt); err != nil {
		return err
	}
	if err := tx.exec(to, amt); err != nil {
		return err
	}
	return tx.commit()
}

func balances(s *store, names ...string) string {
	parts := make([]string, 0, len(names))
	for _, n := range names {
		parts = append(parts, fmt.Sprintf("%s=%d", n, s.rows[n].balance))
	}
	return strings.Join(parts, " ")
}

// evalConcat 化装成"按 SQL 语法解析条件文本"的引擎。
// 真实数据库会解析整段文本；这个模拟器只复现最有代表性的一步：
// 拼接后的文本里出现恒真分支时，条件对每一行都成立。
func evalConcat(cond string) func(name string) bool {
	if strings.Contains(cond, " OR ") {
		return func(string) bool { return true } // OR '1'='1' 恒为真
	}
	lit := strings.TrimSuffix(strings.TrimPrefix(cond, "name = '"), "'")
	return func(name string) bool { return name == lit }
}

// evalParam 是参数化版引擎：文本固定为 name = $1，输入永远只是与字段比较的值。
func evalParam(arg string) func(name string) bool {
	return func(name string) bool { return name == arg }
}

func matchRows(names []string, match func(string) bool) []string {
	var matched []string
	for _, n := range names {
		if match(n) {
			matched = append(matched, n)
		}
	}
	return matched
}

func main() {
	// 路径一：两步全成功 → Commit，草稿一次性生效
	s1 := newStore(map[string]int{"alice": 1000, "bob": 500})
	fmt.Printf("commit 路径   转账前: %s\n", balances(s1, "alice", "bob"))
	err := transfer(s1, "alice", "bob", amount)
	fmt.Printf("  err=%v  转账后: %s\n\n", err, balances(s1, "alice", "bob"))

	// 路径二：第二步入账失败 → Rollback，第一步的扣款被撤销
	s2 := newStore(map[string]int{"alice": 1000, "bob": 500})
	fmt.Printf("rollback 路径  转账前: %s\n", balances(s2, "alice", "bob"))
	err = transfer(s2, "alice", "carol", amount)
	fmt.Printf("  err=%v  转账后: %s\n\n", err, balances(s2, "alice", "bob"))

	// 拼接 vs 参数化：同一个输入，两种通道
	names := []string{"alice", "bob", "carol"}
	concatCond := fmt.Sprintf("name = '%s'", userInput)
	fmt.Printf("拼接版   : SELECT * FROM users WHERE %s\n", concatCond)
	concatMatched := matchRows(names, evalConcat(concatCond))
	fmt.Printf("  条件被当作语法解析 -> 匹配 %d/%d 行（数据变成了代码）\n\n",
		len(concatMatched), len(names))

	fmt.Printf("参数化版 : SELECT * FROM users WHERE name = $1\n")
	paramMatched := matchRows(names, evalParam(userInput))
	fmt.Printf("  参数 = %q -> 匹配 %d/%d 行（输入只是普通字符串，数据留在数据侧）\n",
		userInput, len(paramMatched), len(names))
}

demo 用内存实现复现同样的边界语义；真实项目请使用 database/sql + 对应驱动的事务：Begin、Commit、Rollback 与参数绑定的职责划分完全一致，只是草稿区由数据库管理，defer tx.Rollback()、RowsAffected 检查这些惯用法原样适用。

容易误判的地方

  • "有 Begin 有 Commit 就够了" → 中间任何一步失败都要能走到 Rollback。惯用法是 Begin 之后立刻 defer tx.Rollback()，成功路径用 Commit 收口；只在最后一条语句前开事务，前面的写早已单独生效，原子性仍然不存在。
  • "参数化是替你转义特殊字符" → 转义是拼完了再补，参数化是根本不拼。输入无论含引号、注释符还是分号，都只是与字段做比较的值。
  • "Rollback 能撤销一切副作用" → 边界只覆盖数据库范围内的写。已发出的 HTTP 调用、已发送的消息不在草稿区里，回滚管不到它们；这些需要业务层的补偿或幂等设计，数据库帮不上。

  2. 把 userInput 改成 "bob"。预期结果：拼接版与参数化版都打印 匹配 1/3 行。这印证了机制第 4 步：参数化放弃的不是功能，是"数据越界变成代码"的可能性。
  3. 在 transfer 里删掉 defer tx.rollback()，再把 to 参数改成不存在的 "carol" 运行。预期结果：输出数值不变——但这只靠 exec 失败后草稿恰好没人再动它。真实数据库里，未收口的事务会一直占着连接和锁直到超时；把 defer 加回去，让清理责任回到固定位置。

17 · 测试是设计反馈，不是验收仪式

一句话模型：测试先迫使你把期望结果写清楚，再逼你把依赖隔离出来；表驱动只是表达形式，不是目的。

先看一个现象

有个 ParseID(raw string) (int, error)，把用户输入的字符串转成整数 ID。你写了测试，跑出来是绿的：

go
func TestParseID(t *testing.T) {
    id, err := ParseID("42")
    if err != nil {
        t.Fatal(err)
    }
    _ = id // 没有检查 id 到底是多少
}

你以为"绿灯 = 这个函数对了"，实际这个测试在 ParseID 恒返回 0, nil 时照样通过。它只证明了一件事：这次调用没报错。把断言补成 id == 42，灯才会因为真正的错误变红。

更别扭的是下一步。你想再加一条"空字符串应该报错"，却发现 ParseID 内部直接读了全局的长度上限，还调用了真实的时钟。你没法让时钟停在某个值，也没法让上限在测试里变成另一个数。于是测试不像"验收"，倒像在提醒你：这个函数的边界还没画出来。

先建立直觉

机制拆成三步

1. 红：先把期望写成能核对的值

写一个失败的测试，本质是在回答"给定这个输入，我应该看到什么值"。这是设计动作，不是验证动作：你必须先决定 " 7 " 该返回 7，决定 "4a2" 该返回哪一种错误。没写下来的期望，运行时不会替你补。

为什么必须先红？因为绿灯只能说明"代码没有违反你写过的东西"。一个没有断言、或者断言恒成立的测试，对错误实现完全免疫——它像一把放在桌上却从不拿起来量的尺子。红，意味着这把尺子至少量到过一次差异。

断言还要区分"返回值"和"副作用"。ParseID 是纯函数，核对返回值就够了；如果被测的是"创建订单"，还要核对失败时仓库有没有被调用。返回值正确不代表过程正确。

失败信息也要能定位差异。下面两种写法在失败时给出的信息完全不同：

go
t.Fatal("wrong id")
t.Fatalf("ParseID(%q) = %d, want %d", tc.input, got, tc.want)

为什么后者更重要？测试失败是给未来的维护者看的，他未必写过这段代码。把输入、实际值、期望值一起打印出来，他才能在不读实现的情况下判断是规则变了还是实现坏了。

2. 绿：把不可控的东西变成已知输入

期望写精确之后，下一道坎是可控性。若函数直接读全局变量、调用 time.Now() 或访问真实存储，你只能断言"结果看起来像"，不能断言"结果等于"。

做法不是给测试加魔法，而是把依赖从函数内部挪到调用方：

go
// 依赖作为参数进来：测试给已知值，生产给真实值
func ParseID(raw string, maxLen int) (int, error) { /* ... */ }

// 时间也是依赖：注入一个函数，测试就能把它钉住
type Clock func() time.Time

本篇的 Demo 故意把长度上限做成包级常量，让一张用例表有固定答案；真实项目里同样可以把它改成参数，好让"合法"和"超限"两边都能在测试里精确制造。

时钟是最典型的同类依赖。把 func() time.Time 作为参数传进来，测试就能把时间钉在某个固定点，也能稳定制造"取时间失败"；直接调用 time.Now() 的函数，只能断言"大概对"，因为每次运行的答案都不一样。存储同理：一个只记录调用次数的小 Fake，就能证明失败路径没有产生部分写入。

同一个原则也适用于失败：让依赖返回错误，比等真实故障发生可靠得多。测试里把生成器换成固定返回错误的版本，失败路径就能每次重现，而不是碰运气等一次异常。

为什么这叫隔离而不是"为了面向接口而接口"？因为你只挪走会让结果不可预测的东西：时间、随机、全局配置、外部存储。纯算法不需要额外抽一层，多一层只是多一处要维护的间接。

3. 重构：表驱动是写法，不是质量

用例攒到五六条时，容易冒出一个念头：每条写一个测试函数。很快你会得到五份重复的 if got != want。表驱动把"变化的东西"和"稳定的规则"分开：

go
tests := []struct {
    name    string
    input   string
    want    int
    wantErr error
}{
    {name: "首尾空白", input: "  7  ", want: 7},
    {name: "空串", input: "   ", wantErr: ErrEmpty},
}
for _, tc := range tests {
    got, err := ParseID(tc.input)
    // 同时核对错误语义与成功时的值
}

为什么表驱动不是目的？因为它只改变用例的写法，不改变用例的质量。表里有六行还是六十行，都证明不了边界选对了。真正决定信心的是每行下面那句"这行能挡住什么回归"：空串挡住"忘记去空白"，非数字挡住"把字母当数字"，超长挡住"忘了上限"。写不出这句话的用例，删掉也不可惜。

边界怎么选也有套路，但套路不是"越多越好"：

  • 空值与纯空白：挡住"忘记去空白"和"空串被当成合法"。
  • 刚好越界与刚过界：挡住 <= 写成 < 这类差一错误。
  • 非法类型与方向：挡住把非法输入默认接受，或把有向规则写成双向。

每加一行都问一句"它挡住什么回归"，答不上来就不要加。

18 · 泛型什么时候值得

一句话模型：泛型把"对多种类型重复同一算法"变成编译期类型安全代码；若逻辑依赖具体类型行为，就该用接口或普通函数。

先看一个现象

把整数列表转成字符串标签，再把整数列表平方。两份代码几乎一样：

go
func stringifyIDs(values []int) []string {
    out := make([]string, len(values))
    for i, v := range values {
        out[i] = strconv.Itoa(v)
    }
    return out
}

func squareAll(values []int) []int { /* 同一段循环，只是转换动作不同 */ }

你以为"长得像就该抽成一个函数"，实际抽不抽取决于变化的是不是只有类型。上面两段都是"逐项转换并保持长度"，骨架相同；泛型让这类重复只剩一份：

go
func Map[In, Out any](in []In, f func(In) Out) []Out {
    out := make([]Out, len(in))
    for i, v := range in {
        out[i] = f(v)
    }
    return out
}

反例也马上出现：若算法要调用 v.String()，让元素自己描述自己，any 约束保证不了这个方法存在，编译不过。这时该换的是接口，不是更炫的约束。

先建立直觉

机制拆成三步

1. 泛型是编译期模板，不是运行时容器

普通函数直接写 int、string；泛型函数先写类型参数 In、Out，编译器按调用处的实参把它们确定下来。Mapstring, int 是显式写出，Map(ids, strconv.Itoa) 则由编译器从 []int 和函数签名推断出 In=int, Out=string。

为什么这比 []any 好？因为推断完成后，函数体按具体类型检查和使用：out[i] = f(v) 里 v 就是 int，out 就是 []string，调用方拿到的也是 []string，不必断言。类型错误停在编译期，而不是等到运行时才发现某个元素其实是别的类型。

泛型类型也一样：Result[T any] 在写入 Result[string] 和 Result[int] 时才成为两个具体类型。Go 不做协变，[]Count 不能当 []int 用，即使 Count 的底层类型是 int。

什么时候写显式类型参数？当参数本身提供不了足够线索、你想强调结果类型，或者在调一堆推断错误时。日常调用先让编译器推断，签名更干净；Map[int, string] 这种写法留给需要排除歧义的场合。

2. 约束决定模板里允许做什么

any 表示"什么类型都可以"，代价是函数体几乎什么都不能做。求和需要明确列出允许的类型：

go
type Number interface{ ~int | ~int64 | ~float64 }

func Sum[T Number](xs []T) T {
    var total T // 该类型的零值
    for _, x := range xs {
        total += x
    }
    return total
}

这里三件事同时发生：| 列出类型集；~int 把底层类型为 int 的自定义类型也纳入；var total T 拿到零值，所以空列表自然返回 0。

为什么约束不能靠"看起来相似"？因为编译器只看你列出的类型集，以及这些类型支持的运算。Number 不含 uint、int32，即使它们也能加法；把只支持加法和只支持乘法的类型放进同一联合，函数体也不能同时用 + 和 *。如果算法依赖的是行为而非算术，该用方法约束：

go
func Describe[T fmt.Stringer](v T) string { return v.String() }

comparable 是另一种常见约束，允许 == 和 !=，所以 Slice、Map、函数这些不可比较类型在编译期就被排除。但它检查的是类型参数的类型集合，不是每一个未来的动态值：Equalany 里的动态值仍可能是 Slice，运行时照样 panic。

3. 什么时候该停手

下面这段代码编译不过，它正是"以为泛型能替代具体运算"的典型：

go
func Sum[T any](xs []T) T {
    var total T
    for _, x := range xs {
        total += x // invalid operation: operator + not defined on T
    }
    return total
}

any 没承诺 + 可用，编译器必须在函数体这一关拦下来。修法有两条：真的要算术，就用上一步的 Number 约束；若不同类型各有自己的算法，就别硬塞进一个模板——写两个具体函数，或让它们实现同一个接口。

同样地，把 []any 当"通用版本"常常更糟：每个调用者都要做类型断言，错误被推迟到运行时。泛型也不是性能保证，是否更快要靠 benchmark 和分配分析判断，不能只看"没有接口"。

四种方案可以这样对照：

方案类型安全什么时候用代价
具体函数完整编译期检查只有一种类型，或规则会变多类型时重复实现
泛型函数完整编译期检查骨架稳定、只换类型签名与推断更复杂
接口参数方法调用有静态检查依赖少量共同行为方法要求 + 动态分派
any 参数需断言才能操作真正未知的异构输入错误推到运行时

这张表不是让你挑"最通用"的，而是挑"约束最少又能挡住错误"的。能写具体函数就别急着泛型化。

先预测：Map(nums, strconv.Itoa) 返回值是什么类型？

go
package main

import (
	"fmt"
	"strconv"
)

// 可调参数：演示时取输入列表的前几个元素
const sampleSize = 3

// 可调参数：是否打印 any 版本作对照
const showAnyVersion = true

// Map 把 []In 逐项转换成 []Out，函数体只做遍历、调用 f、写入切片。
func Map[In, Out any](in []In, f func(In) Out) []Out {
	out := make([]Out, len(in))
	for i, v := range in {
		out[i] = f(v)
	}
	return out
}

// mapAny 放弃了类型信息：结果只能当作 []any，取用时要自己断言。
func mapAny(in []any, f func(any) any) []any {
	out := make([]any, len(in))
	for i, v := range in {
		out[i] = f(v)
	}
	return out
}

func main() {
	nums := []int{1, 2, 3, 4, 5}
	n := sampleSize
	if n < 1 {
		n = 1
	}
	if n > len(nums) {
		n = len(nums)
	}
	in := nums[:n]

	labels := Map(in, strconv.Itoa) // In/Out 由参数推断
	var _ []string = labels         // 编译期就确认结果类型
	squares := Map[int, int](in, func(x int) int { return x * x })

	fmt.Printf("输入：%v (%T)\n", in, in)
	fmt.Printf("泛型 Map(strconv.Itoa)：%v (%T)，首项直接是 string：%q\n", labels, labels, labels[0])
	fmt.Printf("泛型 Map(平方，显式实例化)：%v (%T)\n", squares, squares)

	if showAnyVersion {
		anyIn := make([]any, n)
		for i := range in {
			anyIn[i] = in[i]
		}
		anyOut := mapAny(anyIn, func(v any) any {
			return strconv.Itoa(v.(int))
		})
		fmt.Printf("any 版：%v (%T)，首项必须断言：%q\n", anyOut, anyOut, anyOut[0].(string))
	}
}

容易误判的地方

  • "泛型一定比接口快" → 收益首先是类型安全和一份算法。编译器可能生成专用代码，但接口调用、复制和约束检查的成本仍要看实现与测量。
  • "any 更通用，所以优先用它" → 通用来自把检查推给运行时。调用者被迫断言，写错断言的代价远高于编译失败。
  • "类型长得像就能放进联合约束" → 约束列的是类型集，运算取交集。~int 接受底层类型为 int 的 Count，但不让 []Count 自动变成 []int。

自己再做一次

  1. 调用 Map([]string{"a","bb"}, strings.ToUpper)。预期结果：T=string, U=string，输出 [A BB]；两个类型参数相同完全合法。
  2. 把 Map 的转换函数换成 func(x int) (string, error)。预期结果：编译失败，因为当前 Map 的 f func(In) Out 只能返回一个值；要支持失败，得重新设计 Map 或写具体函数。
  3. 给 Sum 的约束加上 ~uint，再传入 Sum([]uint{1,2})。预期结果：返回 uint(3)；但原来的 []int 调用不受影响，因为类型集只做扩展。

19 · 让程序在真实世界活下来

一句话模型：网络会超时、消息会重复、进程会退出；可靠性不是加一层框架，而是给每次操作定义边界、幂等键和停机顺序。

先看一个现象

一笔扣款调用迟迟没返回。客户端等了 50 毫秒就超时，于是重试；服务端其实已经写完账，只是响应在回程丢了，第二次请求又写了一遍。最后用户被扣了两次，而客户端日志写着"第一次超时、第二次成功"，看起来完全合理。

另一个场景：运维发来终止信号，进程立刻退出，正在处理的一半请求被切断，库里留下半条记录。

消息系统也不会帮你保证"恰好一次"：同一条投递可能被消费两次。把重复当成异常去消灭往往徒劳；把它当成常态并设计幂等，系统才会稳定。

你以为"可靠性 = 加一层重试框架"，实际超时只说明本地没及时等到结果，重试则制造了一次新的副作用。两件事叠在一起，才是重复扣款的来源。

先建立直觉

机制拆成五步

1. 超时：先分清"一次尝试"和"整笔操作"

go
ctx, cancel := context.WithTimeout(parent, 50*time.Millisecond)
defer cancel()

context.WithTimeout 给一段工作设截止时刻；到点后 ctx.Done() 关闭，ctx.Err() 变为 context.DeadlineExceeded。它限制的是一次尝试最多等多久。

整笔操作的总预算通常从最外层传下来：

go
total, cancel := context.WithTimeout(r.Context(), 300*time.Millisecond)
defer cancel()
result, err := callWithRetry(total, downstream, key, 3)

为什么光有它不够？三次尝试加退避可能花掉远超 50 毫秒。外层还需要一个总预算，内层每次尝试的超时必须短于外层剩余时间，给排队、序列化和返回响应留出余量。即使每次尝试都没"超时"，重试次数与等待叠加也会把总耗时推高。defer cancel() 则保证定时器在结束时被释放。

更要紧的是：取消是协作式通知，远端可能已经提交了事务。超时保护的是本地资源与延迟，不是回滚。

2. 重试：先分类，再谈次数

go
if errors.Is(err, context.Canceled) || errors.Is(err, context.DeadlineExceeded) {
    return "", 0, err // 预算已耗尽，再发一次没有意义
}

为什么不是所有错误都重试？400、401、404 原样重试不会变好；只有暂时性故障才值得再来。可以先列一张分类表：

错误是否重试依据
连接拒绝、5xx、429通常重试可能是瞬时故障
400、401、404不重试原样再发不会变好
总 Context 到期不重试预算已耗尽

这只是起点：读操作和带副作用的写操作容忍度不同，后者要更保守。每次重试都是一个新请求，因此必须携带同一个幂等键、同样的请求内容——中途改金额或换键，等于把同一笔业务当成两笔。

退避也要设计。连续失败时如果每个客户端都立刻重试，它们会在同一时刻再次压垮下游。常见做法是等待时间按 2 的幂增长，再加一点随机抖动，同时设上限。Demo 为了输出可核对省掉了等待，但保留了"次数上限 + 预算到期就停"这两条硬约束。

本篇 Demo 用计数器让前两次调用固定失败，而不是用随机数。原因很实际：输出必须可核对，读者改一个常量就能重现"两次失败、第三次成功"。

3. 幂等：重复执行只算一次

go
if res, ok := seen[key]; ok {
    return "replay:" + res, nil // 直接重放第一次的结果
}
seen[key] = amount

为什么超时之后重试必须带键？因为你无法从"没收到响应"推出"对方没做事"。键标识同一个逻辑操作，指纹（对规范化请求做哈希）识别这个键是否被挪作他用：同键同请求可重放，同键不同请求应冲突。

指纹是把规范化后的请求体做哈希。字段名顺序、默认值、空白字符都会影响哈希结果，所以"什么算同一个请求"必须先定规则：Demo 用固定字段的结构体，真实系统还要约定精度、时区和可选字段。

边界也要说清：Demo 的 seen 只是进程内 Map。多实例部署时，两个实例仍可能各自接受同一个键；生产要靠共享存储的唯一约束或下游对同一键的去重能力。

4. 优雅停机：取消是通知，不是强杀

go
root, stop := context.WithCancel(context.Background())
// 在途工作监听 root.Done()，收尾后退出
stop() // 发出通知，然后等在途工作结束

为什么不能直接 os.Exit？那样会切断在途请求，留下写了一半的状态。正确顺序是：停止接收新工作 → 通知在途工作收尾 → 等它们真正结束 → 退出。stop() 只发出通知，不会替你撤销已经开始的动作。

顺序写反也很常见：先 stop() 再拒绝新请求，窗口期里仍会有新工作进来；只等固定几秒就退出，慢一点的请求仍被切断。可靠做法是让"不再接收"成为明确的状态位，让"等所有在途结束"有可等待的完成信号。

5. 可观测：把关键数字写下来

Demo 打印重试次数、最终结果、下游调用总数和停机状态。为什么这一步算机制而不是装饰？因为"我们做了可靠性"无法证伪，而"下游调用 3 次、业务成功 1 次、超时 2 次"可以被核对、被告警、被复盘。先想好要打印哪几个数字，再决定在哪里埋点。

数字要记全，事故时才有得查：幂等键、尝试次数、耗时、错误分类、是否重放、停机状态。少一个，就有一段行为无法被检查；字段命名不统一，就只能靠猜。

动手验证

动手验证可控的失败、重试与停机

先预测：failFirst=2、最多 3 次尝试时，下游会被调用几次？

运行：cd examples/minimal/19-failure-in-production && go run .（标有「可调参数」的常量就是旋钮）

go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

// 可调参数：前 N 次下游调用故意失败（用计数器，不用随机数）
const failFirst = 2

// 可调参数：单次尝试的超时（毫秒）
const timeoutMS = 30

type downstream struct {
	attempts int
	seen     map[string]string // 幂等键 -> 第一次的结果
}

func newDownstream() *downstream {
	return &downstream{seen: make(map[string]string)}
}

// charge 模拟一次有副作用的下游调用。
func (d *downstream) charge(ctx context.Context, key, amount string) (string, error) {
	if res, ok := d.seen[key]; ok {
		return "replay:" + res, nil // 命中幂等键，不消耗失败预算
	}
	d.attempts++
	if d.attempts <= failFirst {
		return "", fmt.Errorf("transient failure #%d", d.attempts)
	}
	select {
	case <-ctx.Done():
		return "", ctx.Err()
	default:
	}
	d.seen[key] = amount
	return "charged:" + amount, nil
}

// slow 模拟迟迟不返回的下游，用来展示超时只中断本地等待。
func (d *downstream) slow(ctx context.Context) (string, error) {
	<-ctx.Done()
	return "", ctx.Err()
}

func callWithRetry(ctx context.Context, d *downstream, key, amount string, maxAttempts int) (string, int, error) {
	retries := 0
	for i := 1; i <= maxAttempts; i++ {
		attemptCtx, cancel := context.WithTimeout(ctx, timeoutMS*time.Millisecond)
		result, err := d.charge(attemptCtx, key, amount)
		cancel()
		if err == nil {
			return result, retries, nil
		}
		if errors.Is(err, context.Canceled) || errors.Is(err, context.DeadlineExceeded) {
			return "", retries, err // 预算已耗尽，不再重试
		}
		if i < maxAttempts {
			retries++
			fmt.Printf("  第 %d 次尝试失败：%v → 重试（幂等键=%s）\n", i, err, key)
		}
	}
	return "", retries, fmt.Errorf("all %d attempts failed", maxAttempts)
}

func main() {
	d := newDownstream()

	fmt.Println("场景一：前两次失败，第三次成功")
	res, retries, err := callWithRetry(context.Background(), d, "k1", "100", 3)
	fmt.Printf("  最终：result=%s retries=%d err=%v 下游调用=%d\n", res, retries, err, d.attempts)

	replay, err := d.charge(context.Background(), "k1", "100")
	fmt.Printf("  同键重放：result=%s err=%v 下游调用=%d（未增加）\n", replay, err, d.attempts)

	fmt.Println("场景二：单次尝试超时")
	slowCtx, cancelSlow := context.WithTimeout(context.Background(), timeoutMS*time.Millisecond)
	_, err = d.slow(slowCtx)
	cancelSlow()
	fmt.Printf("  结果：%v（本地没等到 ≠ 远端没做事）\n", err)

	fmt.Println("场景三：优雅停机顺序")
	root, stop := context.WithCancel(context.Background())
	stopped := make(chan struct{})
	go func() {
		defer close(stopped)
		<-root.Done()
		fmt.Println("  [停机] 收到取消通知：停止接收新请求")
	}()
	inflight, inflightRetries, inflightErr := callWithRetry(root, d, "k3", "25", 3)
	fmt.Printf("  [在途] 结果=%s retries=%d err=%v\n", inflight, inflightRetries, inflightErr)
	stop()
	<-stopped
	fmt.Println("  [停机] 在途工作已收尾，进程退出")
}
揭晓 / 核对
验证：cd examples/minimal/19-failure-in-production && go run .。

先运行 demo 核对预测，再对照正文「容易误判的地方」检查自己的模型。

Demo 不证明分布式系统安全。它只让你亲手看到三件事分开写在哪里：尝试的边界、重复的边界、停机的顺序。seen 只在一个进程内，而且前两次失败发生在成功之前——所以它演示的是"同键重放不会增加调用"，不是"响应丢失时也不会重复扣款"。后者要靠下游对同一键去重，或把业务写入与幂等记录放进同一个事务。

容易误判的地方

  • "超时说明对方没有执行" → 超时只说明本地没有及时收到结果。对方可能已提交事务，只是响应丢了；没有幂等保证时，写操作不要盲目重试。
  • "加了幂等键就不会重复" → 键只是协议字段。服务端必须原子地占用键、比较请求内容、保存结果；客户端伪造、跨用户复用和并发竞争都要考虑。
  • "调用 cancel 就等于停机完成" → cancel 只是通知。不等待在途工作收尾就退出，等于主动制造半成品状态；同时，收到通知的工作也可能已经无法撤回。

自己再做一次

  1. 把 failFirst 改成 3。预期结果：场景一打印两次重试提示后返回 all 3 attempts failed，retries=2，下游调用次数=3。
  2. 在场景一成功后，用同一个键 "k1"、不同金额 "999" 再调用一次 charge。预期结果：仍返回 replay:charged:100（不是 charged:999），下游调用次数不变——这正是"同键不同请求应冲突"要提醒的风险。
  3. 把 timeoutMS 改成 500。预期结果：场景二等待更久才打印 context deadline exceeded，场景一与场景三的结果文本完全不变——超时值改变的是等待时长，不是这段代码的结论。
