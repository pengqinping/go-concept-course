# 09 · 共享状态怎么才安全

> 一句话模型：两个 goroutine 同时访问同一变量且至少一个写，就必须建立 happens-before；Mutex 保护的是临界区，不是变量本身。

## 先看一个现象

8 个 goroutine 各给同一个计数器加 1000 次：

```go
counter := 0
var wg sync.WaitGroup
for i := 0; i < 8; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for j := 0; j < 1000; j++ {
            counter++
        }
    }()
}
wg.Wait()
fmt.Println(counter) // 你以为 8000，实际常常小于 8000
```

你以为结果是 8000。实际输出往往是五千多、六千多，而且每次运行都可能不同；加上竞态检测器还会报 `WARNING: DATA RACE`。`counter++` 看起来是一行代码，实际是"读旧值 → 加一 → 写回"三步，交错的goroutine 会从同一个旧值出发，写回两个一样的新值。

再看一个试图补救的写法：

```go
mu.Lock()
tmp := counter
mu.Unlock()

mu.Lock()
counter = tmp + 1
mu.Unlock()
```

你以为"读和写都在锁里，安全了"。实际两个 goroutine 完全可能先后读到 0，再各自写回 1——两次访问确实各自被锁住了，但"读-改-写"这整件事被拆开，中间留出了缝隙。

## 先建立直觉

图说明：上半是竞态时间线——G1 与 G2 都读到 0，各自加一后写回 1，两次更新丢了一次。下半是 Mutex：Lock/Unlock 把整段"读-改-写"圈成临界区，G2 只能等 G1 解锁后读到 1，最终得到 2。右下角标出原子操作的适用范围：单步 `AddInt64` 不可分割，但"先读再判断再写"仍要 CAS 循环或锁。
:::

图上最该带走的一句话：**竞态丢的是更新，不是时间。** 两个 goroutine 都"执行了"加一，但其中一个的结果被另一个覆盖了，从最终数值上看那一次加法像是没发生过。

## 机制拆成四步

### 1. 三个条件同时满足才是数据竞态

- 两个以上 goroutine 访问**同一个变量**；
- 至少有一个访问是**写**；
- 这些访问之间**没有 happens-before 关系**。

为什么全是读就安全？读不改状态，多个读者看到的值一致，互不干扰。为什么必须有第三条？因为"同时"不是指墙上时钟的同一纳秒，而是指"运行时无法证明这两个访问有先后"——只要证明不了，就按可能并发处理。

`counter++` 为什么危险？它展开成 load、add、store 三条指令。G1 和 G2 的 load 都拿到 0，各自的 add 都得到 1，两次 store 都写回 1：两次加法只留下一个 1。这就是典型的**丢失更新**。

### 2. happens-before 不是时间先后，而是结果可见

说"A happens-before B"，意思是 A 的写入对 B 一定可见——B 不会读到 A 写入之前的值，更不会读到"写了一半"的值。它是 Go 内存模型给出的保证，不是我们对代码执行顺序的猜测。

常见的建立手段：

- 同一个 goroutine 内的先后顺序；
- channel 的发送 happens-before 对应的接收完成；
- Mutex 的 `Unlock()` happens-before 随后的 `Lock()`；
- `WaitGroup` 的 `Done()` happens-before 对应的 `Wait()` 返回。

为什么"代码写在前面"不算？因为编译器和 CPU 都会重排指令，另一个 goroutine 又没有任何同步点，它甚至可能永远看不到你的写入。同步不是"等一等"，而是**在两条执行流之间建立一条可见性通道**。

### 3. Mutex 保护的是临界区，不是变量

`Lock()` 与 `Unlock()` 之间的那段代码叫临界区；运行时保证同一时刻只有一个 goroutine 能进入。

```go
mu.Lock()
counter++ // load + add + store 全在临界区内
mu.Unlock()
```

为什么必须把整段"读-改-写"圈进去？只锁写不锁读，读到的就是别人改之前的值；锁了每一步却在中间放开，别的 goroutine 就能插进来重演"都读到 0"。锁的单位是**一段不允许被打断的逻辑**，不是"对某个变量名的访问次数"。

为什么漏掉一次读也会出错？竞态是按"每一次访问"判定的。9 次访问进了临界区、1 次读裸奔，那 1 次就是竞态。判断标准是"这个变量还有没有没被同步覆盖的访问"，而不是"我有没有用过锁"。

通常写 `defer mu.Unlock()` 更安全，但注意 `defer` 要到函数返回才执行：临界区后面若还有长任务，锁会被持有到不该持有的时刻。那种情况就把临界区单独封成一个小函数。

### 4. 原子操作与 channel 各自的边界

`sync/atomic` 的 `AddInt64(&n, 1)` 把"读-改-写"做成一条不可分割的原子指令，比加锁轻。

为什么它不能包办一切？原子性只针对**这一次操作**。"先看 `n` 是否小于上限、再决定是否加一"这种复合逻辑，两步之间仍会被打断，需要 CAS 循环或锁；"账户 A 减 100、账户 B 加 100"这类多个变量的一致性，也不是单次原子操作能保证的。

channel 适合转移数据所有权：数据交出去之后，接收方负责，发送方不再碰。但发送指针不等于转移所有权——两个 goroutine 拿着同一个指针继续改对象，竞态照样存在，仍需新的同步协议。

| 场景 | 合适的工具 |
| --- | --- |
| 单一计数器增减 | `sync/atomic` |
| 多步复合逻辑、多个变量 | `sync.Mutex` |
| 把数据交给另一个 goroutine 处理 | channel |

想亲眼看到阶段 A 的问题，在 demo 目录里跑（这是**故意失败**的可选演示，默认不参与普通测试）：

```bash
go test -tags racedemo -race ./...
```

`race_demo_test.go` 带 `//go:build racedemo` 构建标签，只有显式加 `-tags racedemo` 才会被编译。里面有一个故意不同步的累加：带 `-race` 时竞态检测器会打印 `WARNING: DATA RACE`，并指出两处 `counter++` 的读写位置。这正说明**竞态不由结果判定**：一次运行结果碰巧正确，不等于同步关系成立。平时的 `go test -race ./...` 不会包含这个文件，默认测试保持干净。

Demo 的重点不是记住 8000 这个数字，而是形成一个动作：**看到多个 goroutine 碰同一个变量，先找 happens-before 在哪；找不到，就先把整段读-改-写圈进临界区。**

## 容易误判的地方

- **"结果对了就没有竞态"** → 竞态检测器看的是同步关系，不是某次输出。没有 happens-before，这次碰巧得到 8000 也不能保证下次。
- **"我给读和写分别加了锁"** → 锁必须在整段读-改-写外面；中间解锁就等于给别的 goroutine 留了插队窗口。
- **"用 channel 传了指针就不共享了"** → 指针指向的对象仍被两边持有，竞态按对象算，不按"传了什么"算。

## 自己再做一次

1. 在 demo 里把 `goroutineCount` 改成 1、`increments` 保持 1000。**预期结果**：阶段 B 打印 `期望 1000，实际 1000，一致：true`；单 goroutine 下无锁也必然正确，因为根本没有并发访问。
2. 把阶段 B 的 `mu.Lock()` 移到 `*counter = *counter + 1` 之后（读在锁外，写在锁内）。**预期结果**：`一致：true` 不再有保证，通常仍可能得到 8000——这恰好说明"结果偶然正确"不能证明同步正确；要看到竞态证据，把同样的锁顺序改动同步到 `race_demo_test.go`，再运行 `go test -tags racedemo -race ./...`。
3. 给 `race_demo_test.go` 的并发累加加上 `mu.Lock()/mu.Unlock()` 包住 `counter++`。**预期结果**：`go test -tags racedemo -race ./...` 不再报告 DATA RACE，证明同步关系建立后竞态消失。
