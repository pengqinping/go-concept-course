# 11 · 内存去哪了

> 一句话模型：变量分配在栈还是堆由编译器逃逸分析决定，GC 只回收不可达对象，但"可达"可能来自你没意识到的引用。

## 先看一个现象

一个函数把局部变量的地址返回出去：

```go
func newValue() *int {
	x := 42
	return &x
}

p := newValue()
fmt.Println(*p) // 42
```

你以为 `x` 是局部变量，函数一返回栈帧就被回收，这个指针指向的是一块失效内存。实际 `*p` 稳稳读到 `42`，而且每次调用拿到的都是独立对象——`x` 的作用域结束了，但它指向的那块存储被延长了寿命。

再看一个几乎一样的写法：

```go
func useLocal() int {
	x := 42
	p := &x
	return *p
}
```

这里同样取了 `&`，`x` 却可能根本没进堆，甚至被编译器折叠成常量 `42`。同样是"局部变量取地址"，一个逃逸、一个不逃逸。决定因素不是那个 `&`，而是**这份数据还要活多久**。

再抛一个更隐蔽的：

```go
func counter() func() int {
	count := 0
	return func() int { count++; return count }
}

next := counter()
fmt.Println(next(), next()) // 1 2
```

你以为外层函数一返回，`count` 就随栈帧一起消失；实际两次调用读到 `1` 和 `2`——闭包把 `count` 连同它的存储一起带走了。这三段代码构成了本篇的三个问题：地址能返回、地址可能不逃逸、闭包能延长寿命。

## 先建立直觉

:::figure 11-memory-escape|栈帧、堆与 GC roots
图分两半。上半看"放哪"：`newValue` 的栈帧里 `x` 被取地址，虚线箭头标出它逃逸到堆；调用者的栈帧仍握着指针 `p`。下半看"何时收回"：GC 从三个 roots（全局变量、栈上的指针、寄存器）出发沿指针标记，走得到的堆对象保留，走不到的孤立对象才被回收。两半合起来才是完整答案——逃逸决定存储位置，可达性决定回收时机。
:::

把图记住一句：**编译器管前半段，GC 管后半段，两者用的是不同标准。** 源代码里你看不到"堆"这个关键字，它是编译器替你做的决定。

## 机制拆成四步

### 1. 作用域问"名字在哪可见"，生命周期问"数据要活多久"

`x` 的作用域仅限 `newValue` 函数体，出了花括号这个名字就不存在了。但 `return &x` 把它的地址交给了调用者，调用者可能在函数返回很久之后才解引用。语言必须保证这个操作安全，于是编译器让 `x` 的存储活得比它的名字更久。

这就是栈与堆的真正分界线：栈帧随函数调用压入、随返回弹出，适合"活不过本次调用"的数据；堆由运行时分配器管理，适合"寿命超出当前调用"的数据。它们不是源码上的标签，而是对生命周期需求的回应。

### 2. 逃逸分析是编译期的寿命推断，不是语法规则

编译器在编译期追踪每个值"会不会被当前调用之外的东西引用"。返回地址、存进接口、被闭包捕获、赋值给全局或堆上的结构，都会把寿命传递给函数之外。

为什么 `&x` 不一定是逃逸？因为编译器会顺着指针继续看：在 `useLocal` 里，`p` 只用于一次 `*p`，没有任何副本离开函数，编译器能证明这份数据在栈帧存活期内就能算完，于是把它留在栈上。**取地址只是分析线索，不是结论。**

让编译器把理由说出来：

```bash
go build -gcflags='-m' .
```

日志里的 `moved to heap: x`、`&x escapes to heap` 就是这次编译的判断。注意它是"这次编译的结果"，不是语言规范承诺；内联策略或编译器版本变了，输出也可能变。Demo 里的 `//go:noinline` 只是禁止内联方便观察，并不强制堆分配。

### 3. GC 从 roots 判定可达，不看变量声明位置

分配只是故事的一半。对象什么时候能回收？GC 以 roots 为起点，沿指针遍历所有能到达的对象并标记，剩下的就是垃圾。它不关心对象最初是在栈上还是堆上声明的，只关心"现在还有没有路能走到它"。

为什么这点重要？因为**你以为没人用的对象，可能仍被一条你没注意到的引用拴着**。闭包捕获的变量、接口里装箱的值、全局切片里残留的元素，都是常见的"隐藏的根"。调用 `runtime.GC()` 不会让它们消失——GC 只看可达性。

注意下面这段代码里没有出现一个 `&`：

```go
var saved []any

func keepAlive(v int) {
	saved = append(saved, v) // v 装箱进接口，又被全局切片持有
}
```

`v` 仍然必须活过 `keepAlive`，因为它被装进接口值、又存进了包级变量。判断逃逸时若只盯着取地址符，就会漏掉这类情况。沿着"这个值被谁保存"这条线走，比数 `&` 可靠得多。

### 4. 闭包捕获的是"环境"，不是函数体

`counter()` 返回的匿名函数引用了外层变量 `count`。外层函数早已返回，但函数值被调用者持有，它需要一个地方继续存放 `count`，于是 `count` 被搬到堆，随闭包环境一起存活：

```go
func counter() func() int {
	count := 0
	return func() int { count++; return count }
}
```

每次调用 `next()` 读到的是连续递增的同一个 `count`，不是重新创建的副本。这里逃逸的不是"函数体"，而是被环境引用的那份变量存储。如果闭包只在函数内部短暂使用，编译器完全可能做出不同的决定。

demo 的重点不是记住某个内存数字，而是形成一个动作：**看到一个值，先问"它能活到当前调用之外吗"；看到一个迟迟不降的内存曲线，先问"哪条引用还把它拴在 roots 上"。**

想亲手确认编译器的判断，在 demo 目录运行 `go build -gcflags='-m' .`，对照日志找出 `newValue`、`counter` 里被标注 `escapes to heap` 的变量。

## 容易误判的地方

- **"局部变量一定在栈上"** → 返回地址、闭包捕获、存入接口都会延长寿命，编译器把它挪到堆。栈/堆是分析结果，不是语法标签。
- **"取了 `&` 就一定逃逸"** → 不一定。指针完全在当前调用内使用时，编译器能证明它不逃逸，可能留在栈上甚至优化成常量。判断要问"谁能活过本函数"，不要数 `&`。
- **"调用 `runtime.GC()` 就能释放局部变量"** → GC 不看声明位置，只看可达性。你手里还握着指针的对象，反复 GC 也回收不了；真正要做的是断开那条引用。

## 自己再做一次

1. 在 demo 里把闭包改成"返回后立刻调用"，即写 `fmt.Println(counter()())`，再运行 `go build -gcflags='-m' .`。**预期结果**：仍能看到 `count` 相关对象被分配，因为编译器未必跨内联边界证明它不逃逸；这说明"闭包是否逃逸"要看具体调用方式，不能背结论。
2. 在 `main` 末尾增加 `var keepGlobal = keep`，把切片提升到包级变量，再运行程序。**预期结果**：`HeapAlloc 下降` 这一项不再保证为 true，因为对象被全局变量这条新的根拴住了——这就是"可达来自你没意识到的引用"的现场证据。
3. 用 `runtime.ReadMemStats` 打印 `m.NumGC`，在两次 `runtime.GC()` 之间比较。**预期结果**：`NumGC` 至少增加 2，证明手动 GC 确实触发了；但它不保证任何特定对象被回收，回收与否仍由可达性决定。
